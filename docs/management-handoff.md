# Передача управления между устройствами Android

Двусторонний сценарий реализован общим runtime owner, Native Android bridge и
Compose `ManagementState` / `ManagementScreen`. Это контракт с отдельно
указанными доказательствами; приёмка Android UI остаётся отдельной.
Модель LikeC4 проверена
до реализации. Само наличие `ConsentManagement` и `TransferManagement`
не подтверждает сетевой сценарий.
Требования принадлежат [spec.md](../spec.md#синхронизация-и-доверенные-устройства), композиция —
[wireframes](../wireframes/README.md). Восстановление нового доверенного набора
имеет отдельный [контракт](runtime.md#восстановление-управления-на-android).

## Основа и границы

Передача оставляет ровно одного управляющего в той же БД и том же доверенном
наборе. Прежний управляющий остаётся обычным допущенным участником. Она не меняет
мастер-пароль, ключевую эпоху, состав устройств или пользовательскую историю.
Она требует явного подтверждения отправителя и получателя в открытых сессиях,
а также настоящего аутентифицированного соединения между ними.

Существующий `HandoffConsent` подписывает `previous`, `recipient`, `operation`:
предыдущий control однозначно связывает БД, root, доверенный набор и управляющего.
`ControlChain::transition` проверяет подпись получателя и точную квитанцию
намерения до проверки роли повторяющего переход устройства. Это позволяет
бывшему управляющему подтвердить прежний результат без новой передачи.
`DatabaseService::transfer_management` публикует control и зашифрованный baseline
через единственный coordinator. Эти правила переиспользуются; Kotlin их не
воспроизводит, новых ключей или видов подписи этот сценарий не вводит.

Общий `consent_management` только возвращает подпись, не сохраняет решение
получателя. Решение принадлежит Runtime owner; ManagementProposal/Status дополняют
обычный ciphertext wire. Coordinator не знает о разблокированной сессии.
`NetworkSnapshot.running`, маршрут и успешный прошлый
обмен не доказывают присутствие или готовность получателя. Описанные ниже
обязанности принадлежат runtime owner и платформенным адаптерам; наличие кода
не подтверждает прохождение всех сценариев отказа и перезапуска.

## Идентичность операции и живой доступ

Неизменяемый `ManagementHandoffIntent` содержит `DatabaseId`, закреплённый root,
точный предыдущий control, ID административной операции, DeviceId прежнего
управляющего и получателя. Локальная квитанция дополнительно связана с профилем
и `working_copy`; они не отправляются пиру. ID операции — существующий `Digest`
административных переходов. Повтор передаёт прежнее намерение; иной получатель,
root или предыдущий control под тем же ID даёт несовпадение операции.

На принимающей стороне транспортная идентичность берётся из
`Connection::remote_id`, затем `ControlChain::admit_transport` связывает её с
DeviceId. Поля JSON, endpoint route, текстовое имя устройства и состояние UI
не подменяют эту проверку. Предложение может исходить только от управляющего
этого exact control; статус операции доступен только двум связанным участникам.
Их текущий сетевой допуск также проверяется; старый intent не обходит отзыв.
Публичные названия устройств не добавляются в wire этой работой: используются
существующие проверенные идентификаторы и доступные представления.

Host связывает локальное действие с конкретной слабой command capability
открытого worker и его независимым `WorkerControl`, БД и generation. Глобальный
список `SessionController.statuses()` полезен для инвалидирования, но не позволяет
выбрать произвольный worker вместо явно открытой сессии пользователя.
Внутри runtime это регистрация существующего `Weak<Client>` текущего процесса;
она не удерживает worker живым, не экспортируется UniFFI и не является callback UI.
`OpenManagementBasis` читается одной последовательной командой общего сервиса:
он содержит root/control, локальную identity, управляющего и подтверждённый
применённый baseline. Проверка роли и совместимости остаётся общей Rust-проверкой.

Перед новым предложением, подписанием согласия и исходным commit обе стороны
проверяют актуальный OPEN worker, exact basis и текущую durable coordinator chain.
Получатель отвечает на свежий коррелированный запрос готовности через настоящее
соединение. Ответ связан с текущими worker generation, intent и этой попыткой
соединения; reconnect или lock отзывает это наблюдение. Старый подписанный consent
остаётся квитанцией решения, но не является доказательством текущего OPEN.
Это симметричная проверка: перед явным принятием получатель заново связывается
с исходным управляющим и проверяет его OPEN/basis, а не использует только
ранее сохранённое предложение. Перед commit отправитель получает свежую
готовность уже согласившегося получателя.

После каждого I/O заново проверяется независимый local generation. Если запись
решения закончилась уже после lock, её durable квитанция сохраняется для exact
retry, но callback не утверждает живую готовность и не применяется к закрытому UI.
Status различает сохранённое согласие и текущую Ready/Locked/PendingApply основу.

Отдельный сетевой deadline ограничивает ожидание ответа; ожидание человеческого
решения хранится как состояние, не как бесконечно открытый RPC. Отвечающий handler
не держит mutex coordinator или worker command queue во время ожидания UI/сети.
Проверки независимого контроля доступа не ждут command I/O. Ни один mutex процесса
не удерживается ради предотвращения блокировки телефона.

Ответ о готовности описывает момент проверенного обмена. Удалённое устройство
может заблокироваться сразу после него; протокол не обещает непрерывную доступность
пира. Если исходный commit уже состоялся, такая гонка оставляет подтверждённый
переход с ожидающей доставкой/применением и никогда не возвращает прежнюю роль.

## Порядок и подтверждения

| Фаза | Действие и условие подтверждения |
| --- | --- |
| `Proposed` | Явное «Передать» фиксирует intent на управляющем в защищённом локальном профиле до первой отправки. Ответ UI подтверждает предложение, а не передачу роли. |
| `WaitingDecision` | Получатель проверяет реальную remote identity, root/head и свою OPEN-сессию; сохраняет коррелированное предложение до ответа Pending. Получатель видит отдельное «Принять»/«Отклонить». |
| `AcceptRequested` | Явное принятие сохранено до подписи/публикации consent. После ухода, lock или перезапуска допустим только exact Resume; новое решение или Reject не заменяет этот запрос. Это ещё не Accepted ACK. |
| `ConsentRecorded` | После «Принять» worker создаёт существующий HandoffConsent. Host проверяет актуальность generation/basis и надёжно сохраняет exact consent и решение в профиле **до** ответа Accepted. Подпись в памяти не является этим ACK. |
| `Rejected` | Явный отказ сохраняется до ответа; равный повтор возвращает тот же отказ и не создаёт новый prompt. Отказ допускается до принятого решения; неопределённую публикацию принятия нельзя молча заменить отказом. |
| `SourceCommitted` | Управляющий проверяет свежую готовность получателя и свою сессию, передаёт тот же consent общей TransferManagement. Надёжно опубликованный control + baseline лишает отправителя прежней управляющей роли; успешный ответ требует подтверждения этой публикации. Неопределённый исход блокирует управление до согласования. |
| `AwaitingApply` | Host доставляет существующий signed inventory и ciphertext через обычный обмен. Сохранённый PUT/Offer ACK подтверждает лишь получение; это ещё не успешное завершение передачи управления. |
| `Completed` | OPEN worker получателя проверил и надёжно применил связанный control baseline; общий сервис подтвердил его управляющую роль. Host сохраняет Applied receipt, затем отправляет коррелированный ACK; отправитель сохраняет этот ACK до отображения завершения. |

Локальные фазовые квитанции сохраняет один host-owned `ManagementHandoff` owner
поверх существующего защищённого `NativeProfile` каждого контекста БД. Записи
версионированы и ограничены существующим лимитом защищённого profile store;
повреждение, неизвестная версия и отказ записи не заменяются пустым списком.
Здесь нет пароля, read key, author key, расшифрованного документа или приглашения.
Записи содержат intent, подписанный consent, сохранённое решение/отказ,
последнюю подтверждённую фазу и известный результат control. Они не входят
в Document или журнал пользовательских
версий и не являются новым переносимым форматом архива.

Включая cold owner, nonempty список фаз подтверждается повторной защищённой
записью до возврата. Чтение равных байтов после CommitUncertain само по себе
не позволяет показать Completed/Rejected или забыть исходный запрос.

Wire, consent, control JSON и profile записи не печатаются в логах или ошибках.
Статус передаёт фазу и типизированную причину отказа без значений БД и ключей.
Название выбранной БД для prompt читается из локальной открытой проекции,
а не пересылается как plaintext подпись вместе с предложением.

Применённый результат связывает intent, control самого перехода и фактически
применённые control/baseline. Если после передачи уже были законные последующие
переходы, проверяется их цепочка с exact квитанцией handoff; старый повтор не
возвращает старый baseline и не перезаписывает последующие данные. Доставка может
использовать свежий проверенный inventory, сохраняя прежний ID передачи.

## Применённая роль и неопределённый результат

Полученный coordinator head может уже назначать получателя управляющим, когда
blob/baseline ещё не применён. Такой head показывается как полученный переход;
он не разрешает административные действия. Общий manager guard и
`OpenManagementBasis` обязаны требовать подтверждённое применение baseline
соответствующей цепочки. Это проверяется в сервисе, в том числе для ротации,
политики и приглашения, а не только отключением кнопки Android.

Общий `OpenManagementBasis` сверяет принятую worker основу с текущими
control, baseline, checkpoint и fingerprint persistence port. `can_manage` и
административные действия используют этот guard, поэтому получение нового
snapshot ещё не даёт роль управляющего. `session_authority` или положительный
watermark сами по себе не являются точной квитанцией Applied; ошибка последующего
apply не создаёт управляющих полномочий.

Если публикация source control или локальной квитанции вернула CommitUncertain,
owner удерживает intent и последний подтверждённый этап. Для исходного archive
commit общий сервис сохраняет неизменяемое подготовленное намерение/кандидат
у владельца публикации в worker; host получает только ciphertext через существующий
persistence port. Ни новый baseline из изменённого документа, ни новый случайный
кандидат не заменяют ещё не согласованный исход первоначальной попытки.
Следующий exact retry сначала согласует подтверждённую запись/retained candidate,
а затем продолжает
тот же шаг. Одно чтение равного файла или равенство кешу не выдаётся за durable
ACK. До разрешения неизвестного исхода нельзя запускать другой исходный переход,
выдавать новый operation ID или строить новое согласие от другого head.

Потеря Accepted/Applied ответа решается status-запросом для прежнего intent:
получатель перечитывает/подтверждает сохранённую квитанцию до ответа. Повторный
accept не подписывает другое намерение; retry после SourceCommitted не проверяет
прежнюю управляющую роль как условие доставки и не пишет второй control.
Ошибка доставки после commit отображает «Передача сохранена; ожидается получатель»,
а не «Передача отменена». Бывший управляющий лишён прежних административных
полномочий после единственного commit, также после restart и потерянного ACK.

Lock, фон, закрытие worker и смена поколения немедленно отзывают readiness,
подписание и непринятые callbacks. Durable intent/consent/переход сохраняются.
После unlock незавершённая операция открывается по тому же ID: до commit снова
проверяется свежая готовность обеих сторон, после commit продолжается доставка.
Фоновый ciphertext exchange может завершиться при закрытом worker; Applied ACK
ждёт его нового OPEN и подтверждённого применения. Старый callback не открывает
экран, не раскрывает документ и не возвращает утраченные права.

Изменившийся head до commit делает прежнее предложение устаревшим; оно не
переподписывается автоматически. Новый intent требует нового явного подтверждения
на обеих сторонах. Fork замораживает управление и обмен по текущему контракту;
эта работа не вводит обход через handoff и не изменяет recovery.

## Минимальные интерфейсы и владельцы реализации

Имена ниже фиксируют ответственность слоёв; реализация Native ABI проверяется
отдельной сборкой и Android instrumentation, а не наличием методов в исходниках.

| Слой | Минимальное изменение |
| --- | --- |
| `taypeer-trust/control.rs` | Переиспользовать HandoffConsent, admit_transport, exact transition receipt. Новый формат Control и новая криптография не требуются. |
| `taypeer-services/managed/administration.rs`, `managed/apply.rs` | `OpenManagementBasis` и общий applied manager guard; подписать consent только для exact выбранной основы; сохранить существующий one-commit transfer и подтвердить его точный неизвестный результат без обхода durable ACK. |
| `taypeer-runtime/management_handoff.rs`, host/profile | Единственный owner намерений и фазовых квитанций, weak generation-bound worker registration, versioned protected persistence, reconcile/restart/status. Worker command/author остаётся внутри isolated процесса. |
| `taypeer-sync/wire.rs`, `node.rs` | Ограниченные Proposal/Status/Ready запросы и коррелированные Pending/Accepted/Rejected/Applied ответы. authenticated peer берётся из Connection; fresh Ready не кешируется между соединениями. Новый wire-aware backend без workflow возвращает Unsupported. Действительно старый wire decoder может закрыть stream; Protocol/Transport остаётся неоднозначным отказом, не ложным success или доказательством Unsupported. |
| Runtime network backend | Узкий dispatcher перед существующим ciphertext coordinator: handoff вызывает owner, остальные команды делегируются coordinator. Handler сохраняет Pending/решение до ACK и не открывает БД автоматически. |
| Native `document/management.rs`, Host bridge | DocumentSession: `proposeManagement(recipient, operation)`, `acceptManagement(intent)`, `rejectManagement(intent)`; Host: `managementHandoffs(database)`, `retryManagement(intent)`, явный `managementStatus(intent)`. Host retry продолжает committed delivery без worker, а до commit требует зарегистрированную текущую OPEN-capability и иначе возвращает NeedsUnlock. Typed `ManagementPeerStatusView` отделяет durable phase от fresh Locked/PendingApply/Ready; подпись consent и произвольные author commands не экспортируются Kotlin. |
| Kotlin state/Compose | Удержать immutable запрос и UI generation; показать actual role/phase, явный recipient prompt и direct retry. Не делать сетевой запрос при композиции, не назначать роль по exchange label и не терять запрос при закрытии маршрута. Строки en/ru. |

Для Android это сохранённые маршруты в [taypeer.fig](../wireframes/taypeer.fig),
проверенные по индексу FIG; генератор находится в `wireframes/source/android.js`:

| Board | Saved node ID | Назначение |
| --- | --- | --- |
| `Android / device-menu` | `0:7756` | Действие на выбранном допущенном устройстве. |
| `Android form / transfer-control` | `0:6783` | Выбор получателя и явное исходное подтверждение. |
| `Android form / accept-control` | `0:6811` | Явное решение получателя. |

Кнопка получателя «Принять» не означает, что его роль уже применена. Состояние
«В сети · разблокирован» выводится только из свежего проверенного readiness;
устаревшее наблюдение становится неизвестным/недоступным. Скрытие формы возможно,
но не считается отменой уже опубликованного шага. Recovery-маршрут отдельный.

## Проверки до приёмки

1. Два настоящих Iroh endpoint и независимые worker/профили: предложение,
   явное принятие, один source control, recipient durable apply, ровно один
   управляющий; пароль, эпоха и история пользовательских данных прежние.
2. Третий допущенный peer, подменённый recipient/route/root/head и чужой ID
   операции: типизированный отказ, unchanged files и отсутствие чужого prompt.
3. Получатель locked/Opening/Closing, старый generation, read-only/fork и только
   прошлый успешный exchange: consent/readiness не выдаются. Lock между queued
   signing и ответом не публикует поздний success.
4. Реальные отказы защищённого профиля до/после публикации consent и Reject:
   до durable подтверждения Accepted/Rejected не уходит; exact retry/restart
   возвращает первоначальное решение без нового prompt или изменённого consent.
5. Реальные ошибки source archive до/после публикации: неопределённый результат
   удерживается, exact retry подтверждает одну квитанцию и один control;
   бывший управляющий не может создать приглашение, сменить политику или пароль.
6. Source restart после commit до доставки, потеря Accepted/Applied ACK и
   повтор после более поздних изменений: та же операция, no rollback/duplicate
   control/history, exact повтор не перезаписывает текущий файл.
7. Recipient получил control, но не baseline/blob; затем failure/CommitUncertain
   при apply: управление запрещено **общим сервисом**, Applied ACK отсутствует.
   После корректного durable apply разрешения появляются и ACK подтверждает
   фактическую основу, включая baseline-only ApplyReport с applied=0.
8. Реальный lock/reopen и новый recipient generation после source commit:
   ciphertext сохраняется при lock, completion ждёт application; queued старые
   UI ответы не раскрывают данные и не возвращают экран/роль.
9. Android MainActivity/state тесты маршрутов выбора и принятия/отказа на двух
   реальных worker: никаких fake ready labels, direct retry после ухода/lock,
   сохранность draft-навигации и явное разделение получения/применения.

Числа тестов, покрытия и успешного exchange не заменяют эти проверки.

## Подтверждённая общая реализация

2026-10-07 основной агент выполнил после source freeze:

```sh
rtk cargo test --locked -p taypeer-runtime --features ui-test-support management_handoff -- --nocapture
```

PASS: 5 тестов, 7,96 с; build/run session 82730. Две проверки реального
CredentialStore покрывают ошибки до/после публикации, cold equal-read без ACK,
точный intent и сохранение повреждённой/будущей записи. Три проверки используют
изолированные plaintext worker и настоящие Iroh endpoint: locked Proposal без
prompt, третий допущенный peer, явное принятие/один control/неизменённые epoch и
история, lock/reopen с новым generation, потерянный source commit reply и exact
retry без возврата старой роли. Fixture явно выполняет общий ApplyReceived и
ждёт actual applied basis, а не считает открытие worker доказательством готовности.

Этот результат не подтверждает Native/Android instrumentation, все варианты
restart/отказа из списка выше или физическую приёмку. Отдельного legacy
capability handshake нет: старый decoder может дать неоднозначный transport
refusal. UI не должен выдавать его за отмену уже сохранённого исхода.
