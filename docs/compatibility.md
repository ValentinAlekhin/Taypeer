# Версии, миграции и совместимость Taypeer

Согласовано 2026-09-09. Контракт для [модели данных](data-model.md) и будущего
стабильного формата; продуктовые гарантии закреплены в [spec.md](../spec.md).
Наличие этого документа не подтверждает реализацию миграций или безопасность
контейнера. Проверки перечислены в [testing.md](testing.md#модель-данных-и-эволюция-схемы).

## 1. Независимые версии и идентичности

Номер приложения не является номером БД. Обновление приложения не должно само
по себе переписывать исправный файл или менять доверенный набор.

| Понятие | Что меняется | Чего оно не означает |
| --- | --- | --- |
| Версия приложения | Выпуск macOS/Android-приложения и его поддерживаемые возможности | Автоматическая миграция каждой БД |
| `container_version` | Разбор внешнего файла и его разделов | Версия записи или эпоха ключей |
| `schema_version` | Значение полей документа и правила их объединения/проверки | Версия библиотеки Automerge |
| Формат CRDT-кодирования | Поддерживаемое библиотекой представление исходных изменений и документа | Продуктовая совместимость полей |
| Версии пакета и протокола обмена | Проверка оболочки, сообщений и продолжение передачи | Возможность прочитать зашифрованную нагрузку |
| `local_store_version` | Локальные настройки, регистрация, черновики и маркеры хранения | Изменение переносимой БД |
| Эпоха ключей | Независимый текущий ключ чтения и исторические ключи | Изменение схемы данных |
| Последовательность управления | Подписанная цепочка допуска, отзыва и полномочий | Глобальный порядок пользовательских правок |
| Локальное поколение записи | Очередная атомарная фиксация рабочей копии | Свежесть других устройств или разрешение конфликта |

Версия схемы — положительный последовательно увеличиваемый номер, начиная
со стабильной схемы 1. Значение никогда не переиспользуется с другой семантикой.
Экспериментальные номера не резервируют номера стабильного формата. Для остальных
слоёв независимые пространства версий определяются их проектами.

Формат истории версии фиксируется вместе с её исходной схемой. Декодер текущей
записи нельзя автоматически применять к старой сохранённой версии или пакету.
`DatabaseId`, `TrustSetId`, `RevisionId` и исходные хеши изменений сохраняют
назначение при обновлении приложения и не заменяются номером миграции.

## 2. Контракт чтения, записи и получения

### Дескриптор схемы

Проверяемый `SchemaDescriptor` содержит `schema_version`,
`required_read_features: Set<FeatureId>` и `required_write_features: Set<FeatureId>`.
`FeatureId` — стабильное имя возможности с неизменяемым смыслом. Изменение смысла
требует нового ID. Возможности отражают семантику, а не номер версии приложения.

Дескриптор и переходы схемы привязаны к проверенному состоянию управления и
конкретному документу. Обычный автор не может понизить требования, удалив поле
из Automerge. Читатель проверяет соответствие дескриптора своему известному
контракту схемы; одной декларации отправителя «безопасно игнорировать» недостаточно.
Размещение и аутентификация этих сведений входят в проект формата.

Приложение объявляет поддерживаемые контейнеры, CRDT-кодирования, оболочки,
возможности чтения/записи и реализованные пути миграций. Сетевое объявление
используется для выбора совместимого обмена; оно не заменяет локальные проверки
полученных данных. Последняя известная версия офлайн-устройства — подсказка,
а не доказательство его текущих возможностей.

| Состояние | Чтение документа | Изменение документа | Получение/пересылка |
| --- | --- | --- | --- |
| Поддержаны формат и все обязательные возможности | Да | По обычным правам и состоянию сессии | При поддерживаемом протоколе и допуске |
| Не поддержана обязательная возможность записи | Да, если поддержано чтение | Нет, включая очистку, восстановление и управление | Возможно независимо от чтения |
| Не поддержана обязательная возможность чтения | Нет, требуется обновление | Нет | Возможно при проверяемой оболочке и надёжном хранении |
| Неизвестен/несовместим контейнер или CRDT-кодирование | Нет; исходный файл не переписывается | Нет | Только отдельно поддерживаемые единицы обмена; неизвестный формат не выдаётся за принятый |
| Не поддержан протокол или необходимая проверка оболочки | По последней исправной локальной копии | Если её схема и права допускают | Обмен этой единицей отклоняется без успешного ACK |
| БД заблокирована | Нет | Нет | Да, в пределах возможностей фонового слоя |

«Возможно» не обещает работу старой версии с любым будущим форматом. У фонового
слоя должна быть проверяемая оболочка и совместимый способ надёжно сохранить
точные зашифрованные данные. ACK относится только к действительно сохранённым
единицам. Новая схема не даёт права пропустить проверку подписи, допуска или
лимитов обработки. Повреждение отличается от неподдерживаемой версии.

Чтение при совместимой схеме не требует управляющего устройства. В частности,
актуальное приложение умеет прочитать старый стабильный файл с его паролем без
записи миграции. Установление нового сетевого допуска и восстановление управления
остаются отдельными сценариями.

### Неизвестные поля

Добавление необязательного поля совместимо только при сохранении его смысла для
старого читателя и при доказанной безопасности старого писателя. Писатель должен
сохранять неизвестные значения, варианты конфликтов, расширения и исходные
подписанные данные. Чтение в узкий struct с последующей полной сериализацией
не удовлетворяет этому требованию.

| Изменение | Требование |
| --- | --- |
| Необязательные метаданные, не влияющие на поведение | Допускается совместимое расширение при сохранении неизвестного значения |
| Новый вид ссылки на blob или правило удержания | Старый writer блокируется, если его очистка может удалить нужные данные |
| Новое правило защиты, обязательное для отображения | Требуется возможность чтения; нельзя показывать значение по старым правилам |
| Смена типа/единицы/смысла поля, удаление или перенос поля | Явная миграция и проверка несовместимости; не простое добавление optional |
| Новый вариант enum | Обрабатывается как неизвестное значение по дескриптору, без подстановки старого default |

Переименование метки в UI само по себе не требует переименования хранимого поля.
При несовместимом расширении повышается требование нужного уровня. Даже если
редактирование одного знакомого поля выглядело бы безопасным, отсутствие
обязательной возможности записи переводит весь документ в режим чтения.

Сохранить точную копию исходного файла можно без преобразования его содержимого.
Клонирование сущностей, восстановление и экспорт — семантические операции:
нельзя считать их безопасными только потому, что работает просмотр. KDBX-экспорт
проверяет конфликты, возможность корректной конвертации и показывает отчёт потерь.

## 3. Путь обновления

Гарантия начинается со стабильного формата 1: каждый новый выпуск сохраняет путь
чтения и обновления всех выпущенных стабильных форматов. Внутри приложение может
выполнить цепочку последовательных шагов; пользователь не обязан устанавливать
промежуточные приложения. Неизвестный будущий формат не входит в эту гарантию.

Миграции неизменяемы после выпуска. Исправление ошибки публикуется отдельным
шагом и сопровождается регрессионным примером. Тестовый корпус старых форматов
не перезаписывается новым генератором. Любой короткий путь преобразования должен
давать те же данные, историю и происхождение, что и последовательная цепочка.

| Вид изменения | Исполнитель и условия |
| --- | --- |
| Обновление только приложения | Любое устройство; рабочий документ остаётся прежним |
| Использование уже разрешённого схемой optional-поля | Доверенный writer с нужными возможностями; общая миграция не требуется |
| Повышение общего номера схемы | Управляющее устройство публикует единый проверяемый переход; новая установка приложения не делает это самостоятельно |
| Несовместимая миграция схемы | Явное действие управляющего после разблокировки; атомарная фиксация проверенного кандидата |
| Локальная переупаковка контейнера без изменения общей семантики | Атомарное локальное преобразование после проверки; допустимо только при сохранении подписанных объектов и действующих ограничений записи |
| Локальные настройки/кэш | Мигрируются на данном устройстве независимо от управляющего |
| Зашифрованный черновик | После получения законного доступа к содержимому; исходник сохраняется до успешного преобразования |

Если переупаковка требует изменить подписанное управление, схему или защиту,
она больше не считается только локальной операцией. Смена криптографического
формата не подменяется изменением `schema_version`.

### Запись перехода

`SchemaTransition` содержит `OperationId`, `DatabaseId`, `TrustSetId`, ссылку на
предыдущий переход, исходный и целевой дескрипторы, ID неизменяемого шага миграции,
исходный причинный контекст, связь с результатом и проверенным управлением.
Это техническая запись: она не создаёт строку пользовательской истории.

Состояние схемы определяется единственной проверенной цепочкой, а не максимумом
числа из слияния map. Два противоречащих перехода из одного состояния не выбирают
победителя по времени; они обрабатываются как противоречащее подписанное управление
с остановкой управления/обмена и доступным корректным локальным чтением.

### Транзакция миграции

1. Проверить файл, исходную схему, зависимости, законность текущего управления
   и возможность чтения всего преобразуемого состояния. Неизвестные обязательные
   поля, повреждение и недостаточные полномочия не допускают частичной перезаписи.
2. Показать последствия: необходимость обновления несовместимых клиентов,
   возможное ожидание старых офлайн-правок. Получить
   явное подтверждение перехода; одновременная доступность всех устройств не нужна.
3. Захватить одного локального писателя и зафиксировать исходное поколение.
   Рабочий файл остаётся неизменным до атомарной фиксации кандидата;
   отдельный резервный файл автоматически не создаётся.
4. Создать кандидат состояния отдельно от рабочего файла. Преобразовать текущее
   представление, обеспечить чтение старой истории, сохранить исходные изменения,
   конфликты, отметки очистки, очереди, blobs и происхождение.
5. Проверить кандидата и повторно проверить актуальность исходного состояния
   управления/поколения. При изменении исходника кандидат нельзя фиксировать
   поверх новых данных: выполнить подготовку заново от актуальной основы.
6. Атомарно сохранить результат вместе с переходом, отметками обработки и
   связанными индексами. Обновить локальные маркеры хранения по проверенному
   протоколу фиксации. Показать успех только после надёжной записи.

Сбой до фиксации оставляет старый рабочий файл. Сбой после фиксации, но до ответа
UI, выявляется по записанному переходу: повтор возвращает уже выполненный результат.
Недостаток места учитывает существующий рабочий файл и кандидат, а не только итоговый
размер БД. Незавершённый кандидат не объявляется новым рабочим состоянием.

Получатель перехода проверяет его происхождение и совместимость. Он не запускает
вторую независимую миграцию. До готовности полного поддерживаемого результата
сохраняется последняя исправная применённая копия и статус ожидания; нельзя
соединить номер новой схемы с документом старого представления и разрешить запись.
После принятия несовместимых требований старый writer прекращает запись, сохраняя
неподтверждённый ввод локальным черновиком. Состояния «получено» и «применено»
остаются разными, в том числе при доставке перехода.

Миграция не переписывает исходные подписанные изменения под новым автором.
Её результаты и связи с исходниками записываются отдельно. Для истории требуется
декодер исходной схемы и преобразованное представление при чтении; очистка истории
остаётся отдельным явным действием пользователя.

Automerge предупреждает о конфликтах при независимой миграции нескольких реплик.
Единый управляющий переход — выбранное Taypeer ограничение, а не готовая гарантия
библиотеки. Преобразования зависящих от данных структур всё равно требуют проверки.
[Рекомендации Automerge по моделированию и версиям](https://automerge.org/docs/cookbook/modeling-data/).

## 4. Запоздалые правки старой схемы

Пир может работать со старой копией офлайн, пока не узнает о переходе. Миграция
не отзывает его допуск и не требует заранее собрать все устройства онлайн.

`SourceChange` сохраняет исходную схему, неизменённые байты, хеш, автора,
зависимости и допуск. Обработка идёт по причинным зависимостям, не по времени
получения или клиентским timestamp. Изменение с отсутствующей зависимостью ждёт;
его нельзя объявить независимым из-за смены схемы.

| Случай | Действие |
| --- | --- |
| Представление уже совместимо с текущей схемой | Обычная проверка и объединение на любом подходящем доверенном устройстве |
| Нужен структурный перенос с записью новых изменений | Сохранить источник; преобразование выполняет текущее управляющее устройство |
| Управляющее недоступно или заблокировано | Устойчивое ожидание; текущая схема остаётся доступна для обычной локальной работы |
| Преобразование однозначно | Выполнить автоматически с сохранением исходников, версий и вариантов |
| Преобразование неоднозначно | Сохранить отдельный источник для разбора; не выбирать значение или целевое поле молча |
| В зависимостях впервые принимаются данные отозванного автора | Отдельный просмотр и подтверждение; другие независимые допустимые части продолжаются |
| Целевой объект окончательно очищен | Отдельный разбор поздних правок; автоматического возврата объекта нет |
| Нужного blob нет | Ожидать содержимое, не выдавать восстановленное вложение за готовое |

Однозначность преобразования структуры не разрешает пользовательский конфликт:
все варианты проходят преобразование. Шаг обязан описать соответствие полей,
связей и причинных зависимостей. После переноса правка объединяется с текущими
изменениями по этим зависимостям; её нельзя превратить в присваивание «самого нового»
значения только потому, что преобразование произошло позже.

Для каждого шага предусмотрен адаптер старых исходных изменений. Он выдаёт
результат, требование разбора либо причину ожидания; неподдерживаемое преобразование
не подменяется пустым результатом. Цепочка адаптеров должна работать и после
нескольких пропущенных миграций вместе с пропущенными ротациями ключей.

`ProcessingReceipt` связывает исходный хеш/обработанную часть, переход схемы и
результирующие операции. Он атомарен с результатом, передаётся другим устройствам
и сохраняется при перезапуске и передаче управления. ID зашифрованного пакета
не используется для решения, была ли исходная правка уже преобразована.
Исходная сохранённая версия сохраняет `RevisionId`; техническое преобразование
не добавляет её дубликат в историю.

Передача управления включает принятую цепочку схемы, завершённые отметки и
оставшиеся источники. Новый управляющий продолжает только необработанные части.
Старый не публикует преобразования после утраты полномочий; проверки управления
перед фиксацией и при приёме обязательны. Восстановление нового доверенного набора
не считает старые очереди заново авторизованными: происхождение проверяется по
правилам восстановления, без автоматического объединения независимых наборов.

Неперенесённые источники удерживаются до успешной обработки или отдельного явного
удаления. Обычная очистка истории/корзины не служит разрешением удалить очередь.
Блокировка и отсутствие сети не преобразуют ожидание в ошибочный успешный результат.

## 5. Снимки, восстановление и откат приложения

Обратной миграции в старую схему Taypeer нет. Автоматические снимки перед обновлением
формата или схемы не создаются. Ранее созданные отдельные файлы сохраняют собственное
содержимое и пароль; приложение не обслуживает их. Старое приложение может прочитать
поддерживаемый им файл, но он не объявляется актуальным состоянием после ручной
подмены рабочего файла. Локальные проверки отката не сбрасываются ради downgrade;
один старый файл сам по себе не доказывает, что новейшей копии не существует.

Восстановление данных из выбранного снимка в текущую БД отложено и не входит
в условия первой версии. При возвращении к этому сценарию потребуется отдельный
контракт проверки происхождения и переноса выбранных данных новыми операциями,
без отката актуальной схемы, защиты, управления и отметок очистки.
Восстановление нового доверенного набора остаётся отдельной возможностью.

KDBX остаётся отдельным форматом переноса с отчётом потерь. Экспорт не является
downgrade `.taypeer` и не переносит CRDT-идентичность или доверенные устройства.

## 6. Локальная совместимость и сообщения

Версия локального хранилища независима от схемы БД. Обновление языка/темы не
требует миграции документа. Неизвестный локальный формат не перезаписывается
старым приложением значениями по умолчанию. Перестраиваемый кэш можно создать
заново из проверенных источников; credentials, маркеры отката и черновики кэшем
не являются. Необратимая миграция локального секретного состояния сохраняет
защищённый исходник до успешной фиксации.

Черновик остаётся локальным и не отправляется управляющему для преобразования.
Адаптация неподтверждённой формы не создаёт подписанных изменений старой схемы;
сохранение новой версии возможно только после проверки формы и её исходного
контекста по текущим правилам. При неоднозначности исходник остаётся для разбора.

На границе Rust/UI нужны отдельные результаты: полный доступ, только чтение,
требуется обновление, переход требует управляющего, источник ожидает разбора,
не хватает содержимого, ошибка надёжного сохранения. Это смысловой контракт,
не уже существующие типы публичного Rust/UniFFI API. Допуск и блокировка проверяются
в Rust независимо от отключённых кнопок UI.

| Состояние | ru | en |
| --- | --- | --- |
| Совместимое чтение без записи | Доступно только чтение. Для изменений обновите Taypeer. | Read-only. Update Taypeer to make changes. |
| Неподдерживаемое чтение | Для открытия этой БД обновите Taypeer. | Update Taypeer to open this database. |
| Ожидание преобразования | Изменения сохранены и ожидают управляющее устройство. | Changes are stored and waiting for the managing device. |
| Нужен разбор | Изменения сохранены. Требуется ваш выбор. | Changes are stored. Your choice is required. |
| Не всё содержимое получено | Ожидается содержимое вложений. | Waiting for attachment contents. |
| Несовместимый обмен | Для обмена с этим устройством требуется совместимая версия Taypeer. | A compatible version of Taypeer is required to sync with this device. |

Технические номера и имена возможностей не нужны для обычного действия
пользователя. Диагностика не содержит секретов, приглашений, исходных изменений
или расшифрованных документов.

## 7. Что подтверждено сейчас

В основном workspace модели и API миграций ещё нет. В
[коде контейнера spike](../spikes/encrypted-sync/src/container.rs) есть
экспериментальный контейнер v3 и явный `migrate_v2`; в
[его тестах](../spikes/encrypted-sync/src/container/tests.rs) есть сценарий отказа
неуправляющему, ошибки перед заменой файла и повтора. Это переход экспериментального
контейнера, не миграция продуктовой схемы и не гарантия совместимости приложений.

Текущий [отчёт spike](../spikes/encrypted-sync/REPORT.md) отделяет принятые результаты
исследования от оставшейся приёмки реализации. Сведения о наличии кода сверяются
с исходниками, результаты запуска — с конкретными логами. Эта работа
не переобъявляет прежние эксперименты закрытой проверкой нового контракта.
Файлы spikes не входят в поддержку стабильных форматов и не получают расширение
`.taypeer` простой сменой номера.

До выпуска каждой стабильной схемы обязательны корпус старых файлов, смешанные
версии клиентов, проверки прерываний, преобразования офлайн-правок и независимый
разбор сохранности конфликтов/происхождения. Добавление документации или успешная
проверка каркаса не заменяют эти результаты.
