# Модель данных Taypeer

Обновлено по плану автоматизации 2026-10-05. Это логическая модель и требования к её представлению,
а не реализованная схема или утверждённая байтовая раскладка `.taypeer`.
Продуктовые правила находятся в [spec.md](../spec.md), термины — в
[CONTEXT.md](../CONTEXT.md), эволюция модели — в [compatibility.md](compatibility.md).
Криптография, файловый протокол и ресурсные границы проходят отдельную проверку.

Целевая семантика dev6 ниже запланирована до подтверждения кодом и проверками.
Разделы с именами прежних dev-схем и датированными результатами описывают
исторические срезы, а не приёмку автоматизации. Импорт/экспорт KeePass,
бэкапы и восстановление резервных снимков исключены из релиза.

## 1. Границы хранения

Одна БД содержит один логический Automerge-документ пользовательских данных.
Группы, записи, история и отметки очистки объединяются в нём; содержимое вложений
и изображений находится вне CRDT-журнала, но внутри того же переносимого файла.
Проверенное состояние управления находится в отдельной области контейнера:
обычная запись в Automerge не выдаёт административных полномочий.

| Область | Содержимое | Входит в переносимый файл |
| --- | --- | --- |
| Документ | Метаданные БД, группы, записи, версии, удаления, происхождение восстановлений | Да, зашифровано |
| Бинарные объекты | Содержимое вложений и пользовательских иконок, индекс содержимого | Да, зашифровано |
| Управление и защита | Доверенный набор, подписанные переходы управления, общая политика, текущая и исторические эпохи ключей | Да; публичный минимум определяет проект формата |
| Продолжение обмена | Исходные пакеты, зависимости, неприменённые источники, отметки преобразований и восстановления | Да; содержимое зашифровано |
| Локальное состояние | Приватные ключи, биометрия, черновики, настройки, пути, время доступа, маркеры хранения | Нет |

Связи основных сущностей показаны в представлении `domain`
[общей модели LikeC4](../architecture/data.c4).
Оно описывает нормальное активное состояние. Корзина, конфликт размещения
и окончательная очистка изменяют доступность по правилам ниже;
ссылки на иконки также удерживают бинарные объекты.

## 2. Идентичность и общие типы

Идентификаторы непрозрачны для UI и различаются типами. Они не выводятся из
названия, пути файла или времени создания. Формат их сериализации здесь не задан.

| Идентификатор | Смысл и срок жизни |
| --- | --- |
| `DatabaseId` | Постоянная идентичность БД; сохраняется при копировании, миграции, ротации и восстановлении управления |
| `TrustSetId` | Отдельная линия доверия; восстановление управления создаёт новый ID, обычная ротация — нет |
| `WorkingCopyId` | Локальная рабочая копия; не является сетевым допуском и не переносится как локальная регистрация |
| `DeviceId` | Идентичность устройства в модели допуска; отображаемое имя не участвует в проверке полномочий |
| `GroupId`, `EntryId` | Жизнь объекта, включая корзину и восстановление; клон получает новые ID |
| `AttributeId`, `AttachmentId` | Идентичность элемента записи независимо от его имени; копирование в клон создаёт новые ID |
| `RevisionId` | Одно подтверждение состояния записи, группы или метаданных БД; не меняется при повторной доставке или преобразовании представления |
| `BlobId` | Неизменяемое содержимое в пределах БД; имя вложения и шифрование очередной эпохи не задают его идентичность |
| `OperationId` | Неизменяемая идентичность точной команды или снимка автосохранения; повтор не создаёт новую версию |
| `DraftId` | Локальный черновик рабочей копии; не передаётся другим устройствам |
| `DraftRevision` | Монотонная ревизия ввода внутри одного черновика; не является версией документа или временем |

`Automerge ActorId`, хеш исходного изменения и ID зашифрованного пакета — отдельные
технические понятия. Переупаковка пакета после ротации не создаёт новую сохранённую
версию. Автор CRDT проверяется через подписанное происхождение изменения;
самостоятельно заданный ActorId не доказывает допуск. Новая пишущая реплика не
продолжает скопированный локальный счётчик чужого ActorId.

Копия `.taypeer` сохраняет `DatabaseId`, но не переносит приватные credentials.
Восстановление управления сохраняет идентичность данных и создаёт новую линию
доверия; совпадение `DatabaseId` не разрешает объединять независимые доверенные
наборы. Работа с KDBX исключена из релизного контракта.

Обозначения полей в следующих таблицах:

- `String` — точное Unicode-значение; секреты не обрезаются и не нормализуются.
  Отсутствующее необязательное значение обозначается `None`, пустая строка —
  существующее пустое значение. Чтение и миграция не смешивают эти случаи.
- `Timestamp` — момент UTC с целым числом миллисекунд; `Optional<Timestamp>`
  допускает неизвестное время в импортированных данных. Собственные операции
  фиксируют время создания/подтверждения. Часы служат отображению, а не выбору
  победителя, определению допуска или порядку миграций.
- `Set<T>` — набор без повторов; `Map<Id, T>` — объекты со стабильной адресацией.
  `Optional<T>` означает отсутствие значения, а не удаление сущности.
- `CausalContext` — набор исходных Automerge heads и привязка к линии документа.
  Причинные связи подтверждаются изменениями; значение часов их не заменяет.

Локальное создание проверяет, что новый ID не занят и не принадлежит очищенному
объекту; повторное использование допустимо только для явного восстановления
того же объекта. Ссылки между пользовательскими объектами относятся к одной БД.
При приёме повтор идентичной операции распознаётся, а другое создание с занятым
ID не перезаписывает существующий объект: источник сохраняется отдельно для
разбора. Неверные типы и нарушенные обязательные поля не становятся текущими
данными. Отсутствующая зависимость ожидает доставки; она отличается от
неисправимой структуры. Ограничения разбора и памяти задаются форматом и
проверяются до выделения ресурсов, независимо от продуктового лимита вложений.

## 3. Пользовательские сущности

### Метаданные БД и общая политика

`DatabaseMetadata` содержит `id: DatabaseId`, обязательное `name: String`,
`description: Optional<String>`, `created_at: Optional<Timestamp>`.
Название и описание редактируют доверенные устройства по обычным правилам полей.

`DatabasePolicy` относится к проверенному управлению: лимит одного вложения,
суммарный лимит, целевое время KDF и проверенные параметры защиты. Действующие
значения берутся из принятого состояния управления, не из произвольной CRDT-map.
Только управляющее устройство меняет политику. По умолчанию вложения ограничены
10 МиБ / 100 МиБ, максимум настройки — 100 МиБ / 1 ГиБ; целевое время KDF —
1 секунда при диапазоне 0,5–5 секунд. Мастер-пароль не является полем документа.

### Группа

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | `GroupId` | Неизменяемый |
| `name` | `String` | Обязательное непустое название |
| `description` | `Optional<String>` | Необязательный текст |
| `icon` | `IconRef` | По умолчанию стандартная папка |
| `placement` | `GroupPlacement` | Родитель `Optional<GroupId>` и порядок среди соседей |
| `created_at` | `Optional<Timestamp>` | Не меняется при перемещении |
| `modified_at` | `Optional<Timestamp>` | Производное отображение времени содержательных изменений |

`parent = None` означает верхний уровень. Положение — один атомарный регистр:
конкурирующие перемещения не смешивают родителя одного варианта с порядком другого.
Ключ порядка должен допускать вставку между соседями без перенумерации остальных;
конкретное CRDT-кодирование проверяется до реализации. Одинаковые ключи порядка
разных групп разбираются стабильным сравнением ID, не потерей одной из групп.

### Запись

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | `EntryId` | Неизменяемый |
| `group_id` | `Optional<GroupId>` | `None` означает активную запись без группы, доступную через фильтр «Без группы» |
| `title` | `String` | Обязательное непустое название |
| `username`, `password`, `url`, `notes` | `Optional<String>` | Независимые атомарные поля; пароль всегда защищён в UI |
| `tags` | `Set<String>` | Точные значения, чувствительные к регистру; один атомарно заменяемый набор |
| `expires_at` | `Optional<Timestamp>` | Выключенный срок — `None`; известный момент импорта не усекать до даты |
| `attributes` | `Map<AttributeId, Attribute>` | Элементы независимо адресуются при переименовании |
| `attachments` | `Map<AttachmentId, Attachment>` | Имена и ссылки на содержимое |
| `appearance` | `Appearance` | Независимые поля иконки, основного цвета и фона |
| `created_at` | `Optional<Timestamp>` | Исходное время объекта |
| `modified_at` | `Optional<Timestamp>` | Производное время текущего состояния |

Отдельного сохраняемого порядка записей нет: таблица сортируется локально.
`modified_at` вычисляется из времени пользовательских операций, составляющих
текущее состояние; максимум известных времён служит лишь отображению. Merge,
доставка и техническая миграция не заменяют его своим временем и не создают
конфликт служебного timestamp. Последний доступ находится в локальной модели.

### Атрибуты, вложения и оформление

`Attribute` содержит `id`, `name: String` и атомарное значение
`{ value: String, protected: bool }`. Имя обязательно; одинаковые имена допустимы
при разных ID. Оба элемента сохраняются без переименования и перезаписи;
интерфейс различает строки небольшими метками, не изменяя сохранённые имена.

Значение и признак защиты составляют одну единицу изменения. Так снятие защиты
на одной реплике не открывает автоматически новое секретное значение другой.
Среди конкурентных вариантов защищённая ветка приоритетна; внутри одинакового
уровня защиты используется ранг OpId ниже. Атрибут скрыт и исключён из поиска,
пока существует защищённая конкурентная ветка. Причинно последующее осознанное
снятие защиты разрешено. Альтернативы доступны в истории через явное раскрытие.
Переименование отдельно от изменения значения может объединяться автоматически.

`Attachment` содержит `id`, `name: String` и `blob: BlobId`. Имя обязательно;
совпадающие имена не означают одинаковое вложение. Переименование меняет только
имя; замена файла меняет только ссылку, сохраняя ID вложения. Размер и сведения
о содержимом берутся из проверенного бинарного объекта, а не из введённого имени.
Тип файла не даёт разрешения автоматически выполнять или открывать его.

`Appearance` содержит `icon: IconRef`, `foreground: Optional<Color>` и
`background: Optional<Color>`. `Color` — явный цвет sRGB RGBA, `None` — оформление
темой приложения. `IconRef` — стандартный значок, стабильный ключ встроенного
Lucide-значка либо `BlobId` пользовательского изображения. Для изображения
допускаются метаданные происхождения: файл, favicon или явно заданный URL.
URL не является удалённым хранилищем и не запускает загрузку при чтении.
Пользовательское изображение ограничено 1 МиБ; стандартная папка не требует blob.

Локальный Rust/CLI-срез dev-схемы 3 реализует эти типы: имена и содержимое вложения
изменяются независимо, а удаление сохраняет явный конфликт с конкурентной правкой.
Иконка вместе с происхождением — атомарное поле; основной цвет и фон независимы.
`LucideKey` проверяет принадлежность встроенному каталогу и при десериализации.
[SVG и атрибуция](../resources/lucide/README.md) закреплены отдельной ревизией.
Бинарные байты находятся вне Automerge по [контракту storage](storage.md).

Бинарные команды с `OperationId` сохраняют точный запрос внутри зашифрованного документа,
включая выбранный путь/URL, для отказа при повторном использовании ID с другим
намерением. Это не указание повторно читать файл или загружать URL: подтверждённый
receipt проверяется до I/O. В самом `IconSource::File` локального пути нет.

### Сохранённая версия

`SavedRevision` содержит `id: RevisionId`, адрес записи, группы или метаданных БД,
`schema_version`, `author: Optional<DeviceId>`, `saved_at: Optional<Timestamp>`,
`base: CausalContext`, `kind` и полный логический снимок состояния объекта.
`kind` различает создание, сохранение, клонирование, восстановление и разрешение
конфликта. При импорте неизвестные исходные автор/время сохраняются как неизвестные;
импортирующее устройство фиксируется отдельно как автор операции импорта.

Снимок записи включает группу, поля, атрибуты, оформление и ссылки на вложения;
байты вложений не дублируются. Снимки группы и БД включают их описательные поля.
Новые снимки содержат выбранное состояние. Исходные конкурентные альтернативы
и происхождение удерживаются отдельно до явной очистки; очередное сохранение
не переносит очищенные альтернативы обратно в снимок.
Защита значений сохраняется и в истории. Ссылки на исходные изменения доступны
через индекс происхождения; хеш содержащего изменения не записывается внутрь
самого себя.

Подтверждение записи атомарно сохраняет изменённые поля, одну версию и необходимые
бинарные объекты. Отмена и сохранение локального черновика версии не создают.
Mac сохранил логин, телефон — пароль: обе версии остаются в истории, а объединённое
текущее состояние не получает третью строку. Одна изменившаяся порция автосохранения
создаёт одну версию, включая целую форму группы или БД. Повтор и отсутствие
изменений версии не создают. Восстановление создаёт новую версию,
не переписывая выбранную старую. Миграция сохраняет идентичность
версий и исходное представление; преобразованное чтение не добавляет версии.

Клон записи получает новые ID записи, атрибутов и вложений, но может ссылаться на
те же blobs. Его история начинается с клонирования. Клон группы переписывает
внутренние ссылки всего скопированного поддерева на новые ID.

## 4. Automerge и продуктовые конфликты

Корень документа логически содержит `database`, `groups`, `entries`, `revisions`,
`lifecycle`, `purges` и `recoveries`. Это описание областей ответственности,
а не утверждённые имена байтового формата. Схема связывается с проверенным
состоянием совместимости из [compatibility.md](compatibility.md).

Текущие поля изменяются адресно; сериализация всей типизированной модели обратно
поверх документа запрещена, если она может выбросить неизвестные поля или конфликты.
Текст, включая заметки и пароль, хранится как атомарное значение, не как
посимвольно объединяемый `Automerge.Text`. Составные атомарные значения тоже должны
заменяться целиком, а не становиться несколькими независимо сливаемыми свойствами.

| Ситуация | Результат |
| --- | --- |
| Разные поля или разные элементы по ID | Автоматическое объединение |
| Разные значения одного атомарного поля | Максимальный числовой OpId; все альтернативы доступны в истории |
| Одинаковое значение из параллельных операций | Один отображаемый вариант, исходные операции и версии сохраняются |
| Удаление атрибута/вложения и параллельная правка | Удаление выигрывает; прежнее значение или blob удерживается историей |
| Снятие защиты и параллельная замена значения | Защищённая конкурентная ветка приоритетна |
| Два атрибута с одним именем | Оба элемента доступны по ID без обязательного разбора |
| Входящая правка при открытом редакторе | Не изменять черновик; сохранить локальные изменения относительно его исходных heads |

Редактор хранит исходный контекст и набор изменённых полей. При подтверждении
создаётся изменение относительно этого контекста, затем объединяется с актуальным
документом и проверяется. Поля, которые пользователь не менял, не записываются
поверх входящих. Исходные heads не заменяются актуальными при каждом вводе.
Автоматическая проекция выбирает максимальный OpId: сначала числовой счётчик,
затем байты ActorId. Сравнение строк OpId, часы и порядок доставки запрещены.
Выбор не пишет новую операцию разрешения и не создаёт историю сам по себе.

Конфликт — производное представление исходных операций, а не отдельная таблица
с альтернативной истиной. Его идентичность включает объект, поле/вид конфликта
и набор исходных операций. Альтернативы удерживаются до явной очистки;
выбранное допустимое значение доступно обычным просмотром и копированием.
Обязательного диалога разрешения нет. Защита альтернатив соблюдается в истории.

Automerge сохраняет альтернативы конкурентных присваиваний, но обычное чтение
свойства возвращает одного победителя. Адаптер Taypeer обязан читать все варианты;
числовой ранг и защитный приоритет задаёт общий Rust-контракт Taypeer.
[Описание конфликтов Automerge](https://automerge.org/docs/reference/documents/conflicts/).

## 5. Дерево, корзина и окончательная очистка

`LifecycleOperation` содержит `id`, автора, причинный контекст, вид `trash` или
`restore`, затронутые ID и исходное/выбранное размещение. Удаление группы фиксирует
известное на момент подтверждения поддерево одной операцией. Объекты не копируются
в новую пользовательскую группу «Корзина» и не теряют ID.

Удаление выигрывает у конкурентной правки и перемещения; объект и история
остаются в корзине. Потомки удалённого родителя, включая поздно полученных,
остаются в корзине. Конкурентное перемещение из удаляемого поддерева не отменяет
удаление. Удаление в корзину выполняется сразу с действием «Отменить».

Представление дерева выбирает родительские связи по общему числовому рангу OpId.
Истинная осиротевшая группа поднимается в корень; удалённый родитель не считается
осиротевшим и сохраняет потомков в корзине. Цикл разрывается поднятием в корень
группы с минимальным рангом выбранной родительской связи. При полном равенстве
рангов используется стабильный GroupId. Это вычисляемая проекция без операции
перемещения. Запись без группы остаётся обычной активной записью.

`PurgeRecord` содержит ID операции, автора, причинный контекст и точные ID
окончательно очищенных объектов или версий. Время не служит границей очистки.
Отметки сохраняются для предотвращения возврата данных при повторной доставке.
Очистка известных версий не уничтожает параллельную ещё не виденную версию.
Явная подтверждённая очистка может удалять выбранные альтернативы; следующая
версия не восстанавливает их из прежнего снимка или исходного контекста формы.

После окончательной очистки объекта старая копия не делает его текущим и не
возвращает в корзину. Новые запоздалые правки сохраняются в `PendingSource` для
отдельного просмотра. Явное восстановление создаёт новую операцию и текущую версию
с тем же ID исходного объекта, выбранным назначением и ссылкой на принятую отметку
очистки. Это не снимает отметку с прежних очищенных версий. Действие «Клонировать»
создаёт новый ID по обычным правилам. Повтор восстановления использует устойчивую
отметку обработки, а не создаёт ещё одну копию.

Удаление версии из доступной истории не вырезает её значения из старых операций
Automerge. Первая версия освобождает ненужные бинарные объекты и прекращает
продуктовый доступ к очищенным данным, но не обещает полного уплотнения CRDT,
криптографического стирания или изменения старых снимков и офлайн-копий.
[Модель хранения истории Automerge](https://automerge.org/docs/cookbook/modeling-data/).

## 6. Бинарные объекты и освобождение места

`Blob` содержит `id`, проверенную длину в байтах и неизменяемое содержимое.
Совпадение содержимого определяется в пределах БД независимо от имени и числа
ссылок. Идентификация и зашифрованный индекс дедупликации должны быть проверены
проектом формата; этот документ не выбирает алгоритм хеширования/шифрования
и не вводит публичные отпечатки открытых секретных файлов.

Есть два разных расчёта:

| Расчёт | Что учитывается |
| --- | --- |
| Продуктовый лимит вложений | Уникальное содержимое вложений в текущих данных, доступной истории, корзине и удерживаемых вариантах конфликтов |
| Удержание для физического хранения | Всё перечисленное, иконки и данные, необходимые неприменённым пакетам, преобразованиям и источникам восстановления |

Бинарный объект, используемый только как иконка, не расходует лимит вложений,
но занимает физическое место и подчиняется лимиту изображения. Один и тот же
объект с ролью вложения учитывается в лимите один раз, даже если он ещё и иконка.
Очередь не обходит ошибки физического места; её размер учитывается отдельно
от продуктового лимита. Автоматические резервные копии не создаются.
Ранее созданные отдельные файлы приложение не обслуживает и не включает
в статистику рабочего хранилища.

Зашифрованный пакет может быть надёжно получен раньше связанных blobs.
Это подтверждение конкретно сохранённого пакета, а не полной записи или БД.
Применение, делающее вложение доступным пользователю, завершается только после
проверки и надёжного сохранения нужного содержимого. Зависимые части ждут,
независимые допустимые изменения могут продолжаться.

Сборка мусора выполняется после разблокировки на согласованном состоянии.
Она проверяет все живые ссылки и удержания, а не только отображаемые записи.
Неприменённые источники с ещё неизвестными ссылками запрещают удалять потенциально
нужные им объекты; до проверки допустимо консервативно удерживать весь набор.
Кэш счётчиков ссылок — ускорение, его можно перестроить; он не основание удаления.

После исчезновения последней нужной ссылки новая атомарно сохранённая версия
контейнера исключает байты blob. При сбое остаётся предыдущий исправный файл;
успешная очистка не сообщается до завершения записи. Новые входящие данные не
должны возникнуть между проверкой ссылок и фиксацией результата без повторной
проверки. В заблокированном состоянии эта очистка не выполняется.

Старые ссылки, оставшиеся только в очищенной CRDT-истории и уже обработанных
исходных пакетах, не удерживают blob бессрочно. Их наличие не отменяет очистку.
Если офлайн-правка снова использует такое содержимое, оно должно быть доставлено
заново либо извлечено из выбранного источника; иначе правка ждёт содержимого.
Очищенные версии не предлагаются как полностью восстанавливаемые по одним ссылкам.

При превышении лимита после объединения уже принятые данные сохраняются,
новые добавления отклоняются до очистки или повышения лимита. Неприменённые
данные не удаляются автоматически ради соблюдения лимита.

## 7. Управление, очередь и происхождение

Ниже логические записи; состав публичных полей и подпись их представления
определяет криптографический формат. Названия БД/устройств, содержательные причины
и значения записей не становятся публичными ради фонового обмена.

| Запись | Необходимые данные |
| --- | --- |
| `ControlState` | БД и доверенный набор, предыдущее состояние, последовательность управления, единственный управляющий, допуски/отзывы, эпоха, привязки политики и схемы |
| `KeyState` | Текущая независимая эпоха и бессрочные исторические ключи чтения под актуальной защитой; без приватных ключей допуска/управления |
| `Checkpoint` | Документ и его heads, схема, точное состояние управления, необходимые индексы и привязки к бинарным объектам |
| `SourceChange` | Исходные байты и хеш изменения, авторство, зависимости, версия схемы и привязка допуска |
| `EncryptedPacket` | Идентичность пакета, версия оболочки, проверяемое происхождение, зашифрованное содержимое и эпоха |
| `PendingSource` | Устойчивый ID источника, удерживаемые данные, причина ожидания, зависимости, ход обработки |
| `ProcessingReceipt` | Вид обработки, исходная идентичность/часть источника, переход схемы при необходимости, результирующие ID и причинные связи |
| `RecoveryOrigin` | Источник выбранных восстановленных данных и новые действующие операции; не восстановленный сетевой допуск |
| `InvitationState` | Привязка к БД и получателю, срок действия и однократное использование; секрет приглашения не включается в пользовательский документ |

Причины ожидания различают разблокировку, отсутствующие зависимости/содержимое,
преобразование схемы, разбор отозванного автора и правки окончательно очищенного
объекта. Повреждённые и неподдерживаемые данные не отмечаются применёнными.
Краткая причина может быть доступна UI без раскрытия исходных секретов.

Отметка обработки фиксируется атомарно с результатом и передаётся вместе с БД.
Дедупликация использует исходные изменения/части источника, не ID очередной
зашифрованной упаковки. При частичном переносе отметка охватывает только успешно
обработанную часть; остальная остаётся сохранённой. Противоречащие результаты
одного административного перехода нельзя разрешать обычным CRDT-победителем.

Возможность расшифровать старый источник не даёт права его применить. Проверка
допуска, отзыва и полного замыкания зависимостей предшествует автоматическому
переносу. Разбор выбирает новые изменения действующего устройства с происхождением.
Сохранение истории ключей не обязывает сохранять окончательно очищенные blobs.

## 8. Локальная модель

| Запись | Содержание и защита |
| --- | --- |
| `LocalWorkingCopy` | `WorkingCopyId`, `DatabaseId`, линия доверия, путь/внутреннее размещение Android, локальная идентичность пишущей реплики |
| `DevicePreferences` | Язык, тема, таблица/сортировка, таймеры, relay; доступны в необходимых пределах до разблокировки |
| `LocalCredentials` | Приватные ключи допуска/управления и биометрическая защита; на Linux авторский ключ и независимый LocalStateKey зашифрованы ключом эпохи БД; не содержимое `.taypeer` |
| `LocalState` | Linux: транспортный ключ, регистрация и контрольные отметки под независимым LocalStateKey; без ключей чтения и авторства |
| `Draft` | ID, рабочая копия/БД, цель создания или правки, исходные heads/схема, изменённые поля, введённые значения и собственные зашифрованные бинарные данные |
| `LocalAccess` | Рабочая копия, ID записи, последнее раскрытие/копирование секрета; не создаёт сохранённой версии |
| `StorageAnchor` | Локальное принятое состояние управления и фиксации файла для проверок отката; не переносится как доверие к экспортированной копии |
| `DerivedCache` | Поиск, дерево, конфликты, размеры и прогресс; перестраивается из источников, открытое содержимое удаляется при блокировке |

Черновик не может зависеть от blob, который разрешено удалить очистке рабочей БД:
он удерживает собственную зашифрованную копию нужного содержимого. При ротации
защита локального черновика обновляется либо обеспечивается его открытие через
допустимую историческую эпоху; потеря доступа не скрывается сбросом черновика.
При смене схемы черновик проходит проверку версии до восстановления, исходник
сохраняется при невозможности преобразования.

Преобразование ещё не подтверждённой формы выполняется локально и не передаёт
черновик управляющему. Оно не является переносом уже подписанных старых правок.
После проверки новая форма сохраняется обычным общим контрактом текущей схемы;
если исходный контекст нельзя корректно сопоставить, защищённый исходник остаётся
доступен и возвращается ошибка без сохранения поверх актуальных данных.

Рабочий файл имеет одного локального писателя; повторное открытие того же файла
не создаёт независимого конкурирующего writer. Android-регистрация сопоставляет
повторно выбранную БД с рабочей копией без создания дубликата; совпадение ID
не подменяет проверку файла и линии доверия.

## 9. Связь с кодом и проверками

### Планируемый общий контракт черновиков dev6

`DraftTarget` различает `Entry(EntryId)`, `NewEntry { entry, group }`,
`Group(GroupId)`, `NewGroup { group, parent }` и `Database`. Новые объекты
получают зарезервированный ID; отсутствие группы и родителя допустимо.
`DraftIdentity { draft: DraftId, target: DraftTarget, revision: DraftRevision }`
адресует точный снимок ввода. На границе ответа дополнительно проверяются
DatabaseId, рабочая копия и поколение сессии. Ни target, ни summary не содержат
введённых значений или секретов.

Сервис владеет коллекцией и активным указателем. Планируемые операции —
`drafts`, `resume_draft`, `delete_draft`, `save_draft_snapshot`.
`SaveDraftSnapshot { draft, revision, operation }` сохраняет захваченную ревизию,
оставляя редактор открытым. `DraftSaveOutcome` различает `Saved`,
`LocalDraftSaved` и `Unchanged`; успешный результат содержит идентичность
подтверждённого снимка и OperationId. Ошибки остаются типизированным `Result`.
Режим `SaveDraft` с завершением редактора сохраняется для совместимости
существующих команд; автосохранение использует отдельную операцию.

Черновик содержит версию локального формата, исходную схему/heads, базовое
состояние, набор действительно изменённых полей и точный незавершённый ввод.
Формы группы и БД также сохраняют исходные heads и dirty field set; адресные
`GroupMetadataPatch` и `DatabaseMetadataPatch` используют `Keep / Set / Clear`.
Групповой commit формы создаёт одну версию истории. Отсутствующее изменение
не превращается в повторную запись неизменённых полей поверх удалённых правок.

Неизменяемая попытка связывает DraftId, target, ревизию, OperationId и отпечаток
снимка. Повтор после потерянного ответа использует ту же пару снимок/операция,
даже если появился следующий ввод. Подтверждение продвигает лишь сохранённую
базовую ревизию; продолжение EntryDraft получает новый RevisionId и контекст
точно подтверждённого изменения, сохраняя последующие адресные правки.
Старый ответ не заменяет свежий ввод. Пустая неизменённая форма объект не создаёт.

Коллекция кодируется одним аутентифицированным зашифрованным bundle на рабочую
копию, отдельно от переносимой БД. Удержание blobs — объединение ссылок всех
черновиков и незавершённых снимков. Повторное открытие объекта автоматически
продолжает соответствующий черновик; новые незавершённые формы перечисляются
отдельно. Runtime возвращает при продолжении только маскированное представление;
раскрытие остаётся отдельной явной командой. Точный порядок записи и сверки —
в [контракте хранения](storage.md#автосохранение-и-коллекция-черновиков--целевой-контракт).

Основное [ядро](../crates/taypeer-core/src/lib.rs) содержит типы первого среза:
ID, группы, поля записи, атрибуты и логические версии. Полная модель этой главы
остаётся целевым контрактом: вложения, управление и миграции
в текущий срез не входят. Имена здесь не задают публичный API UniFFI
и не требуют отдельного crate или SQL-таблицы на сущность.
UI получает команды, ограниченные представления и результаты сценариев;
Automerge, ключи и формат контейнера остаются в Rust-сервисах.

В [адаптере документа](../crates/taypeer-document/src/lib.rs) первый срез
реализует один Automerge-документ в памяти, адресные правки от исходных heads,
неизменяемую историю и чтение всех вариантов. Его экспериментальное кодирование
не является схемой стабильного файла. Локальные перемещения, поколения,
корзина и поздние источники реализуются общим API, описанным ниже;
сетевой приём и проверка допуска остаются отдельной работой.

[Прототип контейнера](../spikes/encrypted-sync/src/container.rs) уже исследует
очередь, управление, исторические ключи и миграцию экспериментального контейнера.
Его операции над map/скалярами не реализуют перечисленные сущности, освобождение
blobs или продуктовые миграции схем. Подтверждённые сценарии и ограничения
перечислены в [отчёте spike](../spikes/encrypted-sync/REPORT.md).

Критерии проверки модели находятся в [testing.md](testing.md#модель-данных-и-эволюция-схемы).
До подключения реальных секретов нужно подтвердить хранение, преобразования,
память и ресурсные ограничения на целевых ОС; документ не закрывает эти проверки.

## 10. Историческая реализация локального жизненного цикла

Локальный срез использует поколения состояния при неизменных
публичных ID. Ссылка на родителя хранит ID и поколение атомарно с порядком.
Окончательная очистка закрывает поколение; явное восстановление создаёт новое.
Старые записи и родительские ссылки не направляются в новое поколение автоматически.

Удаление/восстановление хранится в атомарном регистре жизни поколения. Удаление
фиксирует точный набор известных объектов и наблюдавшихся содержательных событий.
Ненаблюдавшиеся правки дают конфликт удаления; дети удалённого поколения также
сохраняются для разбора. Подготовленная операция фиксирует heads и адреса, а
подтверждение не расширяет поддерево.

Содержательное событие связано с поколением, исходным изменением Automerge и,
для записи, сохранённой версией. Отметка очистки сохраняет покрытые события.
Непокрытые события закрытого поколения образуют производный PendingSource;
исходные байты остаются в документе, отметка обработки хранится отдельно.
Время доставки не определяет, является ли изменение поздним.

OrderKey использует проверяемые fractional_index 2.0.2 и путь со стабильными
различителями. Сравнение учитывает ID группы; между совпавшими позициями можно
вставить новый ключ расширением пути без переписывания соседей. Декодер проверяет
байты библиотечным конструктором, а не derived Deserialize библиотечного типа.

Это развитие dev-схемы, не стабильная миграция. Предыдущие dev-файлы отклоняются
без перезаписи; тестовые примеры создаются заново по решению владельца.

Одновременные восстановления одного публичного ID сохраняют отдельные поколения.
Они доступны для просмотра, а обычная проекция не выбирает победителя. Явный
выбор поколения действует на просмотренные heads и сохраняет неувиденный вариант.
Восстановленный родитель не принимает детей со ссылкой на очищенное поколение:
они доступны без размещения до отдельного выбора назначения.

Просмотр PendingSource читает документ в контексте исходного события, а не
случайного текущего победителя. Источник с конфликтом полей/имени требует явного
полного выбора в RecoveryRequest. Receipt сохраняет адрес результата и исходные
ID, hash и actor; исходное представление доступно по ID и после обработки.
Actor обозначает происхождение в локальном CRDT и не доказывает допуск устройства.
Конкурентные непокрытые события остаются самостоятельными источниками.

Операции перемещения, жизненного цикла, клонирования поддерева и извлечения источника
сохраняют результат и OperationId одной транзакцией; файловый сервис публикует их
после надёжного сохранения. Повтор той же команды после перезапуска не создаёт
объектов или строк истории; другой запрос с тем же OperationId отклоняется.
Это не протокол распределённого выполнения одной команды несколькими писателями.

## Историческая реализация описательных метаданных dev5

Форма БД использует дополнительные необязательные ключи Automerge `display_name`
(строка) и `description` (JSON `Optional<String>`). Исходный обязательный `name`
сохраняется для старых читателей; отсутствие `display_name` возвращает его значение.
Группа хранит `description` и `description_modified_at` на своей точной generation.
Это описательные расширения dev5 без изменения контейнера или обязательных features.
Обычные правки сохраняют неизвестные поля. Клонирование/восстановление группы
переносит её известное описание; конкурирующие варианты не выбираются произвольно.
UI отображает признак неоднозначности и не подтверждает такую форму.
[Реализация](../crates/taypeer-document/src/metadata.rs),
[сервисные формы и маскированный редактор](../crates/taypeer-services/src/presentation.rs).

Для обычных команд создания/переименования группы, создания/правки записи,
метаданных БД и подтверждения черновика `lifecycle_receipts` хранит дискриминатор
команды, отпечаток `Digest::object` и первоначальный результат. Секретный ввод
в receipt не дублируется. Namespace пересекается с прежними `operations` и
бинарными/жизненными квитанциями; занятый ID нельзя использовать для другого
запроса. [Сохранение и сверка локального черновика](storage.md#квитанции-обычных-команд-и-подтверждение-черновика)
определяют порядок записи; версия схемы и фиксированный корпус остаются dev5.
