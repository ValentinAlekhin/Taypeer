# Taypeer Rust

Обязательно применять при каждой задаче с написанием, изменением, рефакторингом
или ревью Rust-кода в Taypeer согласно [AGENTS.md](../../../AGENTS.md), включая
тесты, примеры и изолированные spike. Корень репозитория — на три уровня выше
каталога скилла. Все правила кода поддерживаются в этом файле; для их применения не нужно
открывать внешние сайты.

Цель — код, в котором можно найти правило, понять владельца состояния и изменить
один сценарий без каскада несвязанных правок. Улучшать существующие участки в рамках
задачи, сохраняя поведение; наличие скилла не означает, что весь код уже приведён
к этим правилам.

## Перед работой

Применить [taypeer-architecture](../taypeer-architecture/SKILL.md); прочитать
затрагиваемые исходники, тесты и контракт, учесть существующие изменения.
До реализации определить ответственность модуля, инварианты, владельца состояния
и потребителей API. Это часть работы, отдельное согласование не требуется.

[Спецификация](../../../spec.md) определяет поведение,
[словарь](../../../CONTEXT.md) — имена,
[архитектура](../../../docs/architecture.md) — границы компонентов.
Этот скилл задаёт реализацию внутри этих границ и описывает необходимые
идиомы Rust на месте. Не расширять задачу до массовой переработки соседних модулей.

## Декомпозиция и читаемость

- Применять SRP: объединять данные и операции с одной ответственностью и общей
  причиной изменения. Отделять предметные правила, сценарии, преобразование
  внешних данных и отображение. Функция описывает одну понятную операцию;
  шаги разных уровней выделяются в именованные функции.
- Состояние и его инварианты принадлежат конкретному типу. Разделение большого
  `impl` по файлам помогает навигации, но при независимом состоянии выделяется
  отдельный владелец с узким API. Изменение одного экрана не должно требовать
  знания всех внутренних полей окна.
- Применять DRY к правилам и контрактам. Два похожих фрагмента отображения могут
  остаться отдельными, если меняются по разным причинам. Общая функция должна
  выражать понятие, а не принимать набор флагов для несвязанных случаев.
- Применять KISS и YAGNI: выбирать простейшую структуру, решающую текущую задачу.
  Новая абстракция должна устранять конкретное повторение, защищать инвариант
  или изолировать существующую зависимость. Не создавать универсальный framework,
  пустой crate или trait для гипотетического расширения.
- Называть модули и методы по предметной задаче. `utils`, `common` и `manager`
  не становятся хранилищами несвязанных функций; общий helper допустим внутри
  узкой области с ясными потребителями.
- Сначала guard-проверки и ранний возврат, затем основной сценарий. Выбирать
  понятный `match`, цикл или цепочку итераторов; сокращение строк не оправдывает
  скрытые побочные эффекты, вложенные замыкания и сложные сигнатуры.
- Размер файла или функции — повод проверить обязанности, а не самостоятельная
  метрика качества. Жёсткого лимита строк нет; дробление без улучшения владения,
  API или читаемости не считается завершённым рефакторингом.

Модули и поля по умолчанию закрыты. Расширять видимость до `pub(super)`,
`pub(crate)` или `pub` только для конкретного потребителя; не открывать внутренности
ради удобства теста. Rustdoc публичного API описывает смысл, инварианты,
ошибки и существенные побочные эффекты. Комментарий объясняет причину решения.

## Типы, строки и границы данных

- Для закрытых наборов использовать `enum`: язык, тема, вкладка, команда, состояние
  операции. `match` перечисляет значимые варианты; wildcard применять только
  при намеренно общем поведении. Независимый двоичный признак может быть `bool`;
  последовательность неясных булевых аргументов требует именованных параметров.
- Разные идентификаторы и величины с разными единицами оформлять newtype,
  когда их смешение создаёт ошибку. `type EntryId = String` не отличает запись
  от БД на уровне компилятора. Имена брать из словаря проекта.
- Инвариант проверять конструктором или преобразованием. `From` — для
  безошибочного преобразования, `TryFrom`/`FromStr` — при возможном отказе.
  Десериализация не должна обходить проверку типа, который обещает валидность.
  Это правило не запрещает хранить незавершённый ввод в отдельном черновике.
- Различать отсутствие, пустое значение и отсутствие правки. Для адресной правки
  сохранять смысл «оставить / установить / очистить» согласно контракту данных.
  UI не должен молча обрезать пробелы, менять регистр, точность времени или
  нормализовать секреты.
- Ключи хранения (`en`, `ru`, `system`, `light`, `dark`) определяются в одном месте
  рядом с типом; UI работает с типом. Не связывать сериализацию с порядком enum,
  отладочным `Debug` или переведённой подписью. Рефакторинг имени Rust не меняет
  сохранённый ключ; совместимость проверять на фиксированных образцах.
- Именованные константы размещать у владельца значения: например, `FONT_SIZES`
  рядом с настройками. Общий `constants.rs` для всего приложения не вводить.
  Не требуется давать имя каждому очевидному литералу; имя нужно для смысла,
  ограничения или общего источника значения.
- Пользовательские строки размещать в ресурсах en/ru; палитры брать из общего
  TOML. Строковые ключи ресурса, подпись и предметное значение — разные понятия.
  Эталонные литералы в тестах совместимости остаются независимыми от констант кода.

Пример в репозитории — [типы настроек](../../../apps/taypeer/src/preferences/options.rs).

## Владение и время жизни ресурсов

Сначала определить, кто создаёт, изменяет и освобождает значение. Для чтения
строк, коллекций и составных данных предпочитать заимствование (`&str`, `&[T]`,
`&T`); при передаче владения — значение. Небольшие значения `Copy`, например
числа и простые enum, обычно передавать по значению.
`clone()` допустим для нужной независимой копии или разделяемого handle с понятной
семантикой. Он не должен маскировать неверное владение; для секретных данных
каждая дополнительная копия требует оценки её времени жизни.

- `Rc`, `Arc`, `RefCell` и блокировки применять при необходимости разделяемого
  владения или изменения. Указать владельцев и область синхронизации; по умолчанию
  достаточно обычного владения и `&mut self`. `Arc::clone` разделяет владение
  тем же объектом и сам по себе не разрешает изменение. `RefCell` проверяет
  заимствования во время выполнения и может вызвать panic при нарушении правил.
  Циклы сильных ссылок не создавать; обратную невладеющую связь выражать через
  `Weak`, когда она соответствует времени жизни объектов.
- RAII связывает ресурс с владельцем: редактор владеет полями и подписками,
  операция — временными ресурсами. Группировать подписки по времени жизни,
  не кодировать владение индексом в общем векторе.
- `Drop` использовать для освобождения ресурсов, не для подтверждения записи,
  которая может завершиться ошибкой. Явная операция возвращает результат.
  Освобождение памяти не доказывает её затирание; ограничения demo и проверки
  секретов остаются в [архитектуре](../../../docs/architecture.md#сессии-и-секреты).

RAII означает, что ресурс освобождается при уничтожении владеющего им значения,
в том числе при обычном раннем возврате через `?`. Собственный `Drop` нужен только
для дополнительной логики освобождения: поля структуры уничтожаются автоматически.
Завершение процесса или аварийный abort могут обойти деструкторы; надёжность
хранения не должна зависеть от выполнения `Drop`.

## Ошибки и внешние данные

- Ожидаемые отказы возвращать через `Result<T, E>`, обычное отсутствие — через
  `Option<T>`. Ошибки ядра и сервисов должны позволять вызывающему коду различать
  причины по типу или варианту, без разбора текста. Локализация принадлежит UI.
- Распространять ошибки через `?` и осмысленные преобразования на границах.
  `?` возвращает ошибку из текущей функции, но не откатывает уже сделанные изменения.
  Не подменять ошибку пустым списком, успехом или defaults без явного требования;
  особенно различать отсутствующий файл и повреждённый либо неподдерживаемый.
  Игнорирование через `.ok()` или `let _ =` требует понятной причины и безопасного
  поведения при отказе.
- Не применять `unwrap`/`expect`/`panic!` к пользовательскому вводу, файлам,
  сетевым данным и обычным ошибкам платформы. Для доказуемого внутреннего
  инварианта допустим `expect` с объяснением причины; в тестах отказ подготовки
  можно завершать через `expect`/`unwrap`. Это не способ обходить обработку ошибки.
- Проверять данные до изменения состояния. Отказ не должен оставлять частично
  подтверждённую запись. Контракт транзакции, повторного выполнения и надёжного
  сохранения задаёт соответствующий компонент, а не обработчик кнопки.
- Ошибки, `Display`, `Debug`, tracing и тестовые сообщения не раскрывают содержимое
  БД и секреты. Для содержащих их типов нужен безопасный вывод; автоматически
  выведенный `Debug` нельзя добавлять без проверки полей и вложенных типов.

## Выбор паттерна

| Паттерн | Когда применять в Taypeer |
| --- | --- |
| Композиция и чистые функции | Базовый выбор: предметные проверки без I/O, сценарии координируют эффекты, UI отображает результат |
| Узкий trait и адаптер | При существующей границе I/O или подмене часов/хранилища в поведенческом тесте; контракт задаётся потребностью сценария |
| `enum` состояния | Для взаимоисключающих состояний и явных переходов; данные варианта хранятся вместе с состоянием |
| Typestate | Если допустимый порядок вызовов действительно можно проверить компилятором; не заменяет runtime-проверку отозванной или устаревшей сессии |
| Builder | Для сложного конструирования с множеством необязательных настроек; простому типу достаточно конструктора или структуры параметров |
| Параметр типа / `impl Trait` | Когда алгоритм работает с разными реализациями по одному узкому контракту; не делать все слои generic без потребности |
| `dyn Trait` | Когда реализация выбирается во время выполнения или нужны разнородные значения; учитывать косвенность и ограничения API |
| Небольшой макрос | Для устойчивого механического повторения, которое нельзя ясно выразить функцией или типом; вызов должен оставаться понятным |

Композиция и адаптеры следуют [архитектуре Taypeer](../../../docs/architecture.md#границы-реализации).
Применять паттерны с учётом их конкретного устройства:

- Trait содержит минимальный контракт потребителя. Не объединять чтение,
  изменение и управление ресурсом, если потребителям нужны разные возможности.
  Реализация не должна неожиданно менять смысл ошибок и побочных эффектов.
- Параметр типа и `impl Trait` в аргументе дают статический выбор реализации:
  компилятор создаёт специализации, что помогает оптимизации, но может увеличить
  размер кода и сложность сигнатур. Предпочитать конкретный тип, если вариативность
  не нужна. `impl Trait` в возвращаемом значении скрывает один конкретный тип,
  а не позволяет возвращать произвольные разные реализации.
- `dyn Trait` использует косвенный вызов через таблицу методов. Владелец обычно
  хранит `Box<dyn Trait>`, а для заимствования достаточно `&dyn Trait`.
  Trait должен быть совместим с таким вызовом: в частности, вызываемые через
  объект методы не могут иметь собственные параметры типов. Выбор `dyn`
  не отменяет проектирование владения и времени жизни.
- Typestate представляет этапы отдельными типами. Метод перехода принимает
  `self` и возвращает тип следующего этапа; операции недоступны на неподходящем
  типе. Применять, когда такой порядок упрощает API. Для динамического UI часто
  достаточно enum; внешняя блокировка и поколения сессий проверяются во время
  выполнения независимо от типового состояния.
- Builder накапливает параметры и создаёт объект в явном `build`; обязательные
  данные принимаются сразу либо проверяются в `build -> Result<T, E>`.
  Методы настройки не должны неожиданно запускать I/O. Выбрать `&mut self`
  для повторного использования настроек или потребляющий `self`, когда создание
  передаёт владение ресурсами. Не вводить builder для простого конструктора.

Паттерн выбирать по решаемой проблеме; переносить иерархии ООП на Rust механически не следует.

## UI, фоновые задачи и сессии

- Методы отображения компонуют элементы; обработчики передают действие именованной
  команде. Предметная валидация выполняется общим Rust API даже при наличии
  подсказки в форме. Платформенные фокус, ввод и навигация принадлежат клиенту.
- Независимое состояние выделять вместе с командами и ресурсами, которые им
  управляют. Не хранить дублирующие источники одного значения; вычисляемые
  представления получать из актуального состояния.
- Длительный I/O и тяжёлые вычисления выполнять вне потока UI. Для фоновой задачи
  определять владельца, отмену, результат и поведение после закрытия экрана.
  Введение async не делает блокирующий вызов неблокирующим.
- Не удерживать синхронную блокировку, `RefCell`-заимствование или контекст
  изменения UI через `.await`; сокращать критические секции. Async-блокировка
  через `.await` требует обоснованного протокола и отсутствия взаимного ожидания.
- Перед применением ответа или callback проверять актуальность БД, поколения
  сессии и получателя. Для события поля проверять, что оно от текущего экземпляра
  редактора. Отмена задачи дополняет эти проверки, но не заменяет их.
- Блокировка инвалидирует доступ в сервисе, очищает раскрытые значения UI
  и завершает соответствующие подписки. Последующий callback не возвращает
  старое состояние. Контракт — в [архитектуре](../../../docs/architecture.md#сессии-и-секреты).

## Проверки и ревью

Перед завершением оценить изменённый код; при ревью сообщать найденные проблемы
без незаказанных правок:

1. У каждой обязанности и изменяемого состояния понятен владелец; интерфейсы
   позволяют менять внутреннее устройство без правок всех потребителей.
2. Правила не дублируются между UI и ядром; типы сохраняют инварианты, ключи
   хранения и семантику отсутствия/очистки.
3. Ошибки и запоздавшие события не дают ложного успеха, потери данных или утечки;
   ресурсы и подписки завершаются вместе со своим владельцем.
4. Проверки подтверждают наблюдаемое поведение и ошибки, а не повторяют код
   реализации и внутренний порядок вызовов. Для исправленного дефекта добавлена
   воспроизводящая его проверка, когда её можно автоматизировать осмысленно.
5. Выполнен [общий скрипт](../../../scripts/check.sh), результаты и ограничения сообщены
   по [правилам тестирования](../../../docs/testing.md). Новые проверки соответствуют риску
   изменения; успешный неизменённый сценарий не запускается многократно без причины.

Для изолированного spike дополнительно применять его собственные команды
из [docs/testing.md](../../../docs/testing.md) и документации стенда:
общий скрипт не проверяет поведение отдельного workspace.

[Workspace](../../../Cargo.toml) запрещает собственный `unsafe`, `dbg!` и `todo!`,
включает проверку документации; [cargo lint](../../../.cargo/config.toml) запускает Clippy
с `-D warnings`. Новые crates наследуют `[lints] workspace = true`. Форматирование
задаёт Rustfmt. Локальное подавление lint допускается с причиной; глобальное
ослабление проверок ради зелёной сборки недопустимо.

Дополнительные lints включать адресно под обнаруженный класс ошибок.
Группа `clippy::restriction` целиком не включается; её проверки могут противоречить
друг другу. `pedantic` также требует оценки применимости.
Линтер не измеряет декомпозицию и не доказывает безопасность; это остаётся
предметом ревью и соответствующих поведенческих проверок.
