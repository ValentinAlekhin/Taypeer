# Taypeer

Локальный менеджер паролей одного человека для macOS 15+ Apple Silicon,
Android 12+ ARM64 и Linux x86_64 (NixOS/niri/Wayland). [Продуктовые требования](spec.md).

Название продукта — **Taypeer**, расширение БД — `.taypeer`.
Корневая папка локального проекта и папка `wireframes/` не переименованы.
Исторические отчёты и доказательства в `spikes/` сохраняют прежнее имя;
байтовые метки исследовательского криптопротокола не меняются при ребрендинге.

**Стадия:** общий Rust runtime, desktop UI для macOS/Linux и Android UI
для кандидата первого стабильного формата (схема 1). Клиенты используют отдельный процесс на БД;
состав доступных действий и незакрытая приёмка различаются по платформам.
[Запуск macOS](docs/demo.md), [Linux](docs/linux.md), [состояние desktop UI](docs/macos-ui.md).
[Решение по исследованиям](spikes/README.md) разрешает этот этап;
[незакрытые проверки](docs/roadmap.md#безопасность-и-платформенная-приёмка)
остаются обязательными до настоящих паролей.

## Начать разработку

Нужны Rust через rustup и pnpm **10.17.1**. `rust-toolchain.toml` выбирает
проверенный в macOS-стенде Rust **1.97.1** с rustfmt и Clippy.
pnpm устанавливает проектный Node.js **22.22.3** по lockfile.
Для сценарных тестов дочерних процессов нужен Python 3; они используют только
его стандартную библиотеку и публичные искусственные данные.

```sh
pnpm install --frozen-lockfile
pnpm arch:dev
cargo run --locked -p taypeer
sh scripts/check.sh
```

На машине владельца добавляй `rtk` перед командами. Перед каждой задачей сначала
проверь архитектурное влияние; порядок описан в [AGENTS.md](AGENTS.md).
Для отдельных проверок Rust доступны `cargo check-all`, `cargo lint`,
`cargo test-all` и `cargo fmt --all -- --check`.
После загрузки закреплённых зависимостей проверки можно запускать без сети.
Явный офлайн-режим Rust:
`CARGO_NET_OFFLINE=true sh scripts/check.sh`.

Общий скрипт проверяет LikeC4, локальные ссылки, Rustdoc, сборку, поведенческие
тесты Rust, desktop AppView-сценарии на macOS/Linux и конечный `--smoke-test`
без открытия окна. [CI](.github/workflows/ci.yml) настроен на macOS и Ubuntu,
сохранение сборки архитектуры, production Nix-пакет и Windows storage job.
Нативная приёмка платформ и проверки безопасности учитываются
[отдельно](docs/testing.md).

## Кэши сборки

В обычных Rust-сборках отключены debug-символы и incremental-кэш; зависимости
переиспользуются, изменённые локальные crates пересобираются полностью.
Параллелизм сборки и тестов сохраняется. Изолированный `fuzz/` задаёт такой же
development-профиль отдельно; release и sanitizer-профили не изменены.

Из корня checkout на macOS/Linux:

```sh
python3 scripts/build-cache.py          # размеры и preview, без удаления
python3 scripts/build-cache.py --check  # код 1 при Cargo-кэшах свыше 25 ГиБ
python3 scripts/build-cache.py --clean  # разрешённая очистка при остановленных сборках
```

Очистка удаляет только перечисленные incremental-кэши и результаты старых spike.
SDK/AVD, Gradle, основной `target/deps`, release, корпуса, профили и QA evidence
сохраняются. Проверки активных процессов, symlink и tracked-файлов ограничивают
очистку; проверка процессов предварительная, поэтому новые сборки и QA во время
неё не запускают. Полный check выводит отчёт, а обслуживание координируется по
[правилам агентов](AGENTS.md#сборки-и-место-на-диске).

## Платформы и runtime

Desktop и Android используют общий Rust runtime и отдельный процесс БД.
[Контракт и текущие ограничения](docs/runtime.md). Пользовательского CLI нет.

Новые профили используют переносимые зашифрованные credentials без обращения
к системному хранилищу при обычном входе. Первая разблокировка каждой БД после
перезапуска активирует обмен; последующая блокировка сохраняет ciphertext-обмен.
Старые профили и dev-файлы не импортируются автоматически. Windows поддерживается
на уровне библиотеки хранения; клиент для Windows в этот этап не входит.

Linux (NixOS x86_64, Wayland): `nix build path:.#taypeer`, `nix run path:.#`.
`nix develop path:.` предоставляет библиотеки GUI и инструменты разработки.
Профиль, desktop-интеграция и незакрытые проверки описаны в [docs/linux.md](docs/linux.md).
