# Повторная проверка macOS — 2026-09-09

GPUI + GPUI Kit остаются выбранным macOS-фронтендом. Android проверяется
[отдельно на Compose](../android-compose/REPORT.md). Исходный [REPORT.md](REPORT.md)
сохраняет результаты гипотезы общего GPUI-стека от 2026-09-08.

## Изменения стенда

- Добавлен пропущенный `Root::render_dialog_layer`: одного `open_dialog` и внешнего
  Root недостаточно, чтобы стенд рисовал диалог. После изменения диалог наблюдался
  в окне; [снимок](evidence/2026-09-09/dialog-fixed.jpeg). Это не закрывает проблему
  своевременного обновления кадров, описанную ниже.
- Добавлены три режима темы и 14/16/18. Основные роли читаются из того же
  [TOML](../android-compose/palette.toml), что Compose; применяется `Theme::sync_base`.
  Выбор языка/темы/шрифта сохраняется в `target/ui-preferences.txt`, без ввода и сессии.
  Это локальное место хранения изолированного стенда, не продуктовый формат настроек.
- macOS вызывает тот же синтетический Rust `ProbeSession` напрямую. Есть передача
  образца, показ и блокировка. При блокировке заменяется вся сущность редактора
  вместе с подпиской; старый редактор и его undo больше не используются новым полем.
  Потеря активности окна вызывает блокировку; при активации перечитывается тема.
- Добавлены [build.sh](build.sh) и [Info.plist](Info.plist) для повторения `.app`.

## Окружение и повторение

Apple M4, ARM64, macOS 26.6.2 (25G83), Rust 1.97.1.
Kit закреплён полным rev `21f6ce6097c686e98e0ca62ff6178bb4612541a1`, GPUI-pre 0.3.4.
При добавлении общего тестового crate обновлён Cargo.lock, в том числе согласованы
thiserror 2.0.18 и zeroize 1.8.2. Текущий lockfile относится к расширенному стенду,
а не буквально повторяет зависимый граф исходной сборки от 2026-09-08.

Из корня проекта:

```sh
sh spikes/gpui-android/build.sh
cargo +1.97.1 clippy --locked --manifest-path spikes/gpui-android/Cargo.toml -- -D warnings
open spikes/gpui-android/target/Pass2PDesktopProbe.app
```

В локальной RTK-сессии команды запускаются через `rtk proxy` / `rtk cargo`.
Build и Clippy прошли. У транзитивного `block 0.1.6` остаётся предупреждение Rust
о будущей несовместимости. `.app` запускается; macOS 15 отдельно не проверена.

## Расследование ввода и кадров

Использован только публичный образец `SYNTHETIC-ONLY-Жук-42`.

| Действие в исходном настольном стенде | Наблюдение |
| --- | --- |
| `type_text("abc")` | В поле остаётся `c` |
| Отдельные `press_key` для `a`, `b`, `c` | В поле `abc` |
| `type_text` для целой смешанной строки | Потеря части ASCII-символов |
| AX `set_value` для целого образца | [AX возвращает полный образец](evidence/2026-09-09/input-accessibility.txt) |
| Отдельные ASCII key events и `type_text` для кириллицы | [Кириллица не попала в результат](evidence/2026-09-09/input-keys.txt) |

В расширенном стенде несколько кликов не меняли наблюдаемый кадр сразу; после
AX Raise и Tab появились ранее запрошенные диалог и ru. Позднее AX возвращал полный
образец, а захваченный кадр показывал прежнее состояние с диалогом/пустым полем
([AX](evidence/2026-09-09/light-input.txt), [кадр](evidence/2026-09-09/light-input.jpeg)).
Имя файлов `light-input` обозначает попытку смены темы, **не успешную проверку светлой палитры**.
Были также кратковременные ошибки захвата ScreenCaptureKit, после повтора захват работал.

Это позволяет разделить способы доставки текста и воспроизвести расхождение AX/кадра.
Не установлено, какая часть задержки вызвана GPUI, активностью окна или захватом
автоматизации. Исправление отсутствующего слоя диалога не доказывает исправления
IME и цикла кадров. Настоящий клавиатурный ввод и визуальную реакцию без автоматизации
нужно проверить отдельно. Заменять этим наблюдением приёмку ввода нельзя.

## Открытые условия

- Повторить ввод en/ru, composition, выделение/замену/вставку, show/hide и кадры
  на целевой ОС; изолировать минимальный воспроизводимый дефект upstream при подтверждении.
- Пройти обе палитры, system/manual, смену ОС в фоне и активном окне, фокус, скролл,
  минимальный размер, 14/16/18, сохранение выбора после перезапуска. Пока есть сборка
  и отдельные наблюдения, полной визуальной приёмки нет.
- Проверить native clipboard, файловые диалоги и биометрию/защищённый ключ на macOS;
  соответствующие платформенные упражнения ещё не реализованы в настольном стенде.
- Проверить блокировку ОС, завершение процесса, старые ответы, память редактора
  и Rust/JVM-копий. Удаление сущности редактора не доказывает затирания всей памяти.

**Статус macOS-пункта этапа 1: частично выполнен.** Новая сборка и локальный дефект
стенда исправлены; полную UI-матрицу и проблему кадров закрывать ещё нельзя.
