# Проверка формата и зашифрованного обмена

**Статус: spike завершён как исследование 2026-09-09; результаты приняты с ограничениями.**
45 тестов контейнера v3, сети и хранения прошли на macOS и ARM64 AVD Android 12.
Ротация, Iroh direct/relay, KDF, 10 снимков и миграция проверены. Проба памяти
выявила незатёртые аллокации Automerge; отдельный процесс проверен как кандидат
границы секретов. Реальный телефон, полный rollback и полный формат ещё нужны.
Кандидат схемы и библиотеки выбраны только для опыта, production-формат не утверждён.
Результаты: [REPORT.md](REPORT.md), проект: [DESIGN.md](DESIGN.md). Основание: [spec.md](../../spec.md), раздел
«Криптографический формат и фоновый обмен».

## Результат, который требуется получить

Проверенный проект и изолированный сценарный прототип с искусственными данными.
Проект должен объяснять не только штатный обмен, но и действия после сбоя,
блокировки, отзыва и восстановления. Сборка примера Iroh/Automerge недостаточна.

## Содержание проекта

- Модель угроз и границы доверия: файл, локальное устройство, допущенный/отозванный
  пир, relay, резервные копии, источник некорректных данных.
- Версионируемый контейнер: открытый заголовок, аутентификация, шифрование,
  ограничения размеров и ресурсов, неизвестные версии и повреждения.
- Ключи и полномочия: сетевые credentials, ключи чтения, управляющее устройство,
  биометрическая защита, локальные черновики; кто что имеет в locked/unlocked.
- Argon2id: калибровка при базовых 64 МиБ и цели 0,5–5 секунд, допустимые минимумы,
  верхние пределы для недоверенного заголовка, проверка фактического времени.
- Зашифрованные изменения: авторство, метаданные, проверка без расшифровки,
  защита от подмены/повторов, надёжное сохранение и условия подтверждения пиру.
- Разблокировка: проверка содержимого, причинность, идемпотентное применение,
  конфликтные варианты, история, безопасные границы уплотнения/очистки.
- Одноразовые приглашения, подтверждение, передача единственного управления,
  отзыв, смена пароля и несколько пропущенных ротаций.
- Переносимость файла с паролем без автоматического допуска; старый снимок,
  восстановление управления в новый доверенный набор и независимые наборы.
- Атомарная запись и 10 предыдущих исправных снимков, миграции, сбои на каждом
  этапе, нехватка места и восстановление после остановки процесса.
- Выбор проверенных криптобиблиотек и работа с памятью; анализ и проверка проекта
  перед переносом кода в продукт. Тесты прототипа не являются внешним аудитом.

## Минимальные сценарии прототипа

| Сценарий | Что подтвердить | Статус |
| --- | --- | --- |
| A разблокирован, B заблокирован, C получает через B | B надёжно хранит/пересылает без ключей чтения; применение после unlock | См. результат ниже |
| Сбой записи перед подтверждением | Нет ложного ACK, исправная копия читается, повтор обмена завершается | См. результат ниже |
| Повторы и перестановки доставки | Нет дубликатов, причинные зависимости учитываются | См. результат ниже |
| Повреждение файла/пакета, неизвестная версия, чрезмерные параметры KDF | Ограниченный отказ без перезаписи и чрезмерного потребления ресурсов | См. результат ниже |
| Одноразовый код: истечение, повтор, отказ управляющего | Допуск не выдаётся | См. результат ниже |
| Отзыв B и поздние изменения B | После принятого отзыва нет автоматического применения; старая история сохраняется | См. результат ниже |
| Две пропущенные ротации и старый снимок | Явное восстановление/новый вход по проекту; прежняя биометрия не обещает доступа | См. результат ниже |
| Передача управления и прерывание | Успех оставляет одного управляющего; определено восстановление незавершённой операции | См. результат ниже |
| Файл + пароль на новом устройстве | Чтение возможно; сетевой допуск/управление не появляются автоматически | См. результат ниже |
| Потеря управляющего | Новый набор, ключи и пароль; старые допуски не переносятся | См. результат ниже |
| Блокировка при несохранённой форме и ошибка записи черновика | Открытые данные удаляются, ошибку восстановления видно | См. результат ниже |

Подробные результаты каждого сценария и пределы доказательства —
в [REPORT.md](REPORT.md#сценарии-и-пределы-доказательства). Нативный Android-код
исполнялся на эмуляторе; это не проверка готового APK, биометрии или lifecycle UI.

## Запуск на macOS

Из корня репозитория; на машине без RTK уберите префикс:

```sh
rtk cargo test --manifest-path spikes/encrypted-sync/Cargo.toml --features network --locked --release
rtk cargo fmt --manifest-path spikes/encrypted-sync/Cargo.toml --check
rtk cargo clippy --manifest-path spikes/encrypted-sync/Cargo.toml --features network --all-targets --locked -- -D warnings
rtk cargo run --manifest-path spikes/encrypted-sync/Cargo.toml --locked --release
rtk cargo run --manifest-path spikes/encrypted-sync/Cargo.toml --bin memory-probe --locked --release
rtk sh scripts/check.sh
```

`network` запускает настоящие отдельные QUIC-процессы и локальный self-signed relay,
ему нужен доступ к loopback. Без feature сетевые тесты не выполняются. Обычный
`cargo run` калибрует цели 0,5/1/5 секунд. `memory-probe` возвращает **2** при
обнаружении незатёртого canary Automerge — это сохранённый отрицательный результат,
не команда с ожидаемым успехом. Основной `scripts/check.sh` spike не запускает.

## Android ARM64 emulator

Установите JDK 17, commandlinetools и SDK packages `platform-tools`, `emulator`,
`system-images;android-31;google_apis;arm64-v8a`, `ndk;27.2.12479018`,
`build-tools;35.0.0`; примите SDK licenses. Создайте и запустите ARM64 AVD Android 12.
Для Rust нужен target `aarch64-linux-android`. Значения путей ниже относятся
к измеренной сессии; при повторе укажите свой SDK/JDK и serial из `adb devices`.

```sh
export ANDROID_SDK_ROOT=/tmp/pass2p-android-sdk
export JAVA_HOME=/Library/Java/JavaVirtualMachines/temurin-17.jdk/Contents/Home
rtk sh spikes/encrypted-sync/scripts/build-android.sh
rtk proxy python3 spikes/encrypted-sync/scripts/android-check.py \
  --build-json spikes/encrypted-sync/target/android-harness/build.json \
  --adb "$ANDROID_SDK_ROOT/platform-tools/adb" --serial emulator-5554 \
  --dex spikes/encrypted-sync/target/android-harness/classes.dex \
  --jni-library spikes/encrypted-sync/target/aarch64-linux-android/release/deps/libtaypeer_encrypted_sync_spike.so \
  --output spikes/encrypted-sync/evidence/android.log
```

Скрипт копирует только синтетический стенд в `/data/local/tmp/taypeer-spike-suite`.
Iroh-процессы запускаются через Java/JNI и получают настоящий Context до Endpoint.
`app_process` использует системный Context под adb shell: это не API для будущего
приложения, которому нужен Application Context из Kotlin. Runner требует успеха
45 тестов и отдельно фиксирует ожидаемую отрицательную диагностику памяти (exit 2).

## Дополнительные эксперименты

С установленными cargo-fuzz 0.13.2 и nightly; из каталога spike:

```sh
rtk cargo run --bin fuzz-seeds --release --locked -- fuzz/corpus/parser
rtk proxy env RUSTUP_TOOLCHAIN=nightly cargo fuzz run parser -- -max_total_time=60 -max_len=8192 -rss_limit_mb=1024 -timeout=5
```

`fuzz/` имеет собственные workspace/lockfile; corpus и результаты сборки игнорируются.
В [evidence](evidence/) сохранены логи тестов, KDF, отрицательной пробы памяти,
fuzzing, advisory и лицензий. Cargo audit запускался с закреплённым снимком RustSec
DB; точная ревизия указана в отчёте. Лицензии — инвентаризация, не разрешение выпуска.

`disk-probe` предназначен **только** для отдельного пустого тестового тома:
режим `full` создаёт filler до ENOSPC с ограничением 64 МиБ. Нельзя указывать рабочий
том. В опыте использован 32-МиБ HFS+ disk image; после заполнения и повторного
монтирования read-only проверены отказ записи и неизменность предыдущего файла.
Команды и вывод — в [storage-os.md](evidence/storage-os.md).
