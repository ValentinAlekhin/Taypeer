# Кандидат формата и модель угроз

Обновлено: 2026-09-09. Это экспериментальный проект, **не утверждённый формат
`.taypeer` и не прошедший аудит протокол**. В этом spike нет продуктовой реализации UI.
Согласованное поведение описывает [spec.md](../../spec.md), результаты —
[REPORT.md](REPORT.md).

## Ключи и доверие

Чтение содержимого, подпись изменений и управление допуском — разные полномочия.
Переносимый файл с паролем позволяет читать БД, но не содержит приватных ключей
подписи/допуска/управления. В опыте одна Ed25519 identity играет роль автора и,
для управляющего, подписанта control. Отдельные OS-хранилища этих credentials,
биометрия и жизненный цикл приватных ключей не реализованы. В сетевом стенде
Ed25519 identity также аутентифицируется настоящим QUIC-соединением Iroh.

| Противник | Граница |
| --- | --- |
| Файл без пароля | Офлайн-перебор; Argon2id повышает цену, AEAD обнаруживает подмену содержимого |
| Файл и пароль | Чтение и изменение собственной копии, без нового сетевого допуска |
| Сеть/relay | Задержка, повтор, подмена; видны автор, эпоха, размер и публичная история управления |
| Допущенный злонамеренный автор | Может подписать мусор или ложные значения; подпись не доказывает корректность продуктовых данных |
| Отозванный автор | Сохраняет старые ключи; расшифровка его пакета не даёт права применения |
| Копия управляющего ключа | Две подписи допустимы по отдельности; встреча ветвей останавливает обмен |
| Локальный администратор/rollback всего устройства | Защита от чтения памяти, замены файлов и отката не доказана |

Предпосылка хранения: один честный писатель и приватная временная директория.
`Store` перечитывает последнее поколение с диска перед каждой операцией, не держит
ключей чтения. `State`, Automerge и исторический набор ключей остаются обычными
аллокациями; применение `Zeroizing` к KEK/буферам **не доказывает очистку памяти**.
Нужны исследования копий, KDF workspace, swap/core dumps и блокировки на ОС.

## Версия 3: единый контейнер

Исполняемая реализация — [container.rs](src/container.rs). Старые `Snapshot`,
`LockedInbox` и бинарный `P2PSPIKE` версии 1 оставлены в [lib.rs](src/lib.rs) только
для регрессионных опытов. Новый сценарий их файловую раскладку не использует.
Расширение `.taypeer` не используется. `Store::migrate_v2` — явная локальная
миграция v2 → v3 с актуальным паролем и управляющим ключом; исходный файл
сохраняется отдельно. Сеть принимает только v3, автоматической миграции нет.

Внешний JSON версии 3 содержит:

- поколение атомарной записи;
- публичный закреплённый корень и подписанную цепочку control;
- подписанный зашифрованный checkpoint и отдельный management baseline;
- непрозрачную очередь исходных подписанных изменений, включая карантин;
- доказательства обнаруженного fork;
- зашифрованные источники восстановления и локально удержанные checkpoint;
- журнал привязанных приглашений с хешами токенов и признаком использования.

Checkpoint подписан текущим допущенным автором, связан с точным хешем control,
ID набора и эпохой. Control проверяется от корня, закреплённого вызывающей стороной.
JSON-сериализация нормализует ID пакета. Неизвестная версия, повреждённые подписи,
чужой набор или нарушенная цепочка отклоняются до перезаписи.

При принятии следующего control исходную принятую историю задаёт **baseline с
подписью управляющего**, связанный с точным head. При handoff разрешена подпись
предыдущего управляющего. Чужой member checkpoint не становится baseline:
иначе участник мог бы объявить непринятую историю отозванного автора уже принятой.
Отдельный отрицательный тест воспроизводит этот обход версии 2 и проверяет отказ v3.

Локальный `.local-anchor` хранит SHA-256 всего поколения и подготовленный следующий
хеш. Он обнаруживает откат/удаление очереди при неизменном маркере. Это локальный
журнал одного писателя, **не** OS-защищённый счётчик и не подпись переносимого manifest.
При удалении/откате всего каталога защита исчезает. Новый читатель не может узнать
свежесть по одному старому файлу. Маркер не экспортируется вместе с контейнером.

## Парольная обёртка и исторические ключи

`SealedState` содержит version/group/epoch/control, параметры KDF и соль,
парольную AEAD-обёртку текущего случайного ключа и отдельный AEAD payload.
Payload — документ, применённые change hashes и набор ключей всех эпох.
Обе AEAD используют разные nonce и domain suffix (`/wrap`, `/content`), метаданные
входят в AAD. Подпись checkpoint покрывает обе части.

KEK из актуального пароля оборачивает только актуальный независимый read key.
Этот ключ защищает содержимое и исторический набор. При ротации создаются новый
пароль и независимый ключ, все старые read keys сохраняются без срока удаления.
Новый ключ никогда не оборачивается старым. `open_key` открывает старый payload
через сохранённый read key, обходя потребность в старом KEK, но не проверку AEAD.
Никаких приватных ключей допуска/управления в историческом наборе нет.

Примитивы прежнего опыта сохранены:

- [Argon2id 0.5.3](https://docs.rs/argon2/0.5.3/argon2/), version 0x13,
  соль 16 байт, выход 32 байта, 64–256 МиБ, t=3..256, p=1.
  Калибратор выбирает t по измерению при 64 МиБ, максимум за четыре прогона;
  цели 500–5000 мс, допуск измерения ±20%, без искусственного ожидания.
  `calibrate_kdf` доступен управляющему и сохраняет профиль в следующем
  подписанном control/checkpoint. До явной калибровки fixture использует t=3.
- [XChaCha20Poly1305 0.10.1](https://docs.rs/chacha20poly1305/0.10.1/chacha20poly1305/),
  ключ 32 байта и случайный nonce 24 байта из OsRng. Это готовая конструкция
  библиотеки, собственные криптографические примитивы не реализуются.
- [Ed25519 verify_strict](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/struct.VerifyingKey.html#method.verify_strict),
  отдельные домены для изменения, привязки допуска, checkpoint и control.
- SHA-256 для идентификаторов; [zeroize](https://docs.rs/zeroize/1.9.0/zeroize/)
  защищает только явно обёрнутые буферы, не весь граф приложения.

Это кандидаты опыта, не утверждённые минимумы или аудит всего протокола.
[RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html) даёт профиль 64 МиБ/t=3/p=4;
p=1 и измерения эмулятора не заменяют выбор параметров на целевом телефоне.

## Получение и автоматический перенос

`receive` проверяет актуальный допуск транспортного пира; сетевой стенд передаёт
identity из `Connection::remote_id()`, а не из тела запроса,
исходную подпись и привязку пакета к конкретному control. Через действующего пира
можно сохранить старый пакет отозванного автора для просмотра. Сам отозванный пир
допуска не получает. ACK возвращается только после атомарной записи всего файла.
`export` пересылает контейнер без ключей чтения.

`receive_container` проверяет цепочку и принимает более новое управляющее состояние
с management baseline. Локальная очередь сохраняется. Уже применённая локальная
история удерживается в зашифрованном checkpoint до следующего успешного сохранения
разблокированного состояния. Чужие удержанные checkpoint не импортируются как
разрешение автоматически принять историю отозванных авторов. При равном или более
старом control чужой checkpoint не заменяет локальный: изменения идут через пакеты.

После актуального пароля проверяются AEAD, Automerge change и соответствие actor
подписанному автору. Для ещё не принятого change проверяются все состояния допуска
от исходного control до текущего, включая промежуточный отзыв и повторный допуск.
Замыкание зависимостей проверяется полностью **до** вызова `apply_changes`:

| Результат | Значение |
| --- | --- |
| `AutoApply` | Автор непрерывно допущен, все зависимости уже приняты или также допустимы |
| `NeedsReview` | Автор либо хотя бы одна ещё не принятая транзитивная зависимость требует просмотра |
| `AlreadyApplied` | Исходный change hash уже есть в принятом документе |
| `AwaitingDependencies` | В замыкании отсутствуют необходимые исходные changes |

Если одновременно есть отзыв и отсутствующая зависимость, сначала выдаётся
`AwaitingDependencies`; после её получения выполняется повторная оценка.
Независимые допустимые изменения продолжают применяться. Исходные bytes/hashes,
author, deps и промежуточные версии сохраняются; значение поля не переписывается
операциями нового автора. Повторная упаковка одного change не создаёт новую версию.

Документация изучена через навык Context7:
[Automerge history](https://automerge.org/docs/reference/glossary),
[конфликтные значения](https://automerge.org/docs/reference/documents/conflicts).
Context7 выдаёт преимущественно JS/conceptual docs; точные Rust-сигнатуры сверены
с установленным исходником закреплённой версии 0.7.4. Проверки используют `get_all`,
`get_change_by_hash` и `fork_at`, не только выбранное Automerge значение.

## Просмотр и восстановление

`review` материализует только причинное состояние выбранного source change в
отдельном Automerge-документе. Непринятые зависимости не попадают в рабочий документ.
`extract` принимает явный список путей и вариантов и создаёт новый change действующего
устройства. Его зашифрованное сообщение содержит operation ID, source hash, выбранные
пути и исходные authors/hashes. Оригинал остаётся в очереди с прежним статусом;
извлечение не восстанавливает допуск и не разрешает исходные revoked deps.
Для зависимой правки пользователь может извлечь выбранные значения из её причинного
состояния тем же путём. Остальная допустимая очередь обрабатывается независимо.

Схема редактора/извлечения в опыте — строковые поля во вложенных map.
Восстановление копии поддерживает map и скалярные значения. List/text и неоднозначные
конфликтные значения снимка отклоняются до изменения БД; выбор сложных объектов,
полная схема записей/вложений/корзины и UI остаются вне этого этапа.

`restore` открывает старый checkpoint историческим ключом актуальной БД, создаёт
отдельную `before-restore-<operation>` копию, затем восстанавливает содержимое новыми
операциями. Текущие пароль, ключи, control, manager и membership сохраняются.
Исходный зашифрованный снимок остаётся в контейнере для происхождения и старой истории.
Текущая история также сохраняется; служебные recovery receipts не откатываются.

Receipt операции находится в самом Automerge-документе и синхронизируется вместе
с новой версией. Повтор с тем же ID/выбором возвращает тот же change hash после
повторного durable save; другой выбор с тем же ID отклоняется. Для нового намеренного
восстановления вызывающая сторона создаёт новый ID. Исходные пакеты не удаляются;
API явного удаления пока нет.

## Управление, приглашения и fork

Control остаётся подписанной линейной цепочкой group/seq/epoch/manager/members/previous.
Ротация требует управляющего и нового пароля; удаление member требует новой эпохи.
Перед ротацией сохраняется отдельная `before-rotation-<seq>` копия.

Приглашение создаёт OsRng token 256 бит. `InvitationCode` предоставляет длинный код
и JSON payload для QR; QR-рендерер отложен вместе с UI. Журнал связывает хеш токена
с group, manager, recipient и временем истечения now+300 секунд. Предъявление другой
identity/БД, истечение и повтор отвергаются. Явный `approved` моделирует подтверждение
управляющего. Consumed и новый допуск фиксируются **одной** атомарной записью.
Отказ также потребляет приглашение. После неоднозначного сбоя выданный допуск читается
из сохранённой цепочки; повторно использованный код не становится новым приглашением.
Iroh проверяет настоящую identity предъявителя; управляющий стенд явно выбирает
approved до обработки запроса. UI и QR-рендерер отложены.

Противоречащие подписанные ветви сохраняются как доказательство; управление, приём,
пересылка и применение останавливаются, в том числе после перезапуска. Если запись
fork не удалась, текущий объект Store остаётся остановленным; после рестарта до
durable evidence требуется повторная доставка доказательства. Диск, отказавший до
записи, не может гарантировать сохранение обнаруженного события.
Чтение остаётся доступно. `recover_trust` создаёт новый файл с независимым group,
ключом и единственным новым manager; старые сетевые допуски не переносятся.
Старый файл со всей неприменённой очередью остаётся на месте.

Превентивная защита от скрытого fork при краже/копии управляющего ключа вне первой
версии. `HandoffConsent` подписывает разблокированный получатель, согласие связано
с текущим control. Управляющий надёжно записывает relinquish до доставки successor
получателю; сбой доставки оставляет паузу без действующего управляющего на получателе.
Повтор согласия идемпотентен. Direct/relay-тесты передают successor и проверяют,
что старое устройство больше не управляет, а новое может выполнить ротацию.
Само согласие в тесте создаётся локально, UI-протокол его получения ещё нужен.

## Хранение, память и транспорт

`atomic_save`: копия `.previous` → temp/write → file sync → rename → directory sync.
На macOS после fsync вызывается F_FULLFSYNC. Новые файлы имеют mode 0600;
конечные symlink для target/temp/previous отвергаются, temp открывается O_NOFOLLOW.
Это не защита от гонок замены родительских директорий; каталог должен быть приватным.

`storage::commit` сохраняет предыдущий контейнер в `.backups` (10 снимков), пишет
подготовленный local-anchor, атомарно заменяет контейнер и фиксирует финальный anchor.
Данные, hashes, receipts, очередь и control фиксируются в одном поколении. После
rename ошибка означает отсутствие ACK, а не обещание отката; повтор перечитывает
целое состояние. Незавершённый anchor допускает только подготовленное старое/новое
поколение. Отдельные копии перед ротацией, восстановлением и миграцией не входят в 10.
Проверены пять injected fault, exit дочернего процесса до/после rename, ENOSPC и
read-only том macOS. Это не отключение питания и не проверка контроллера накопителя.

`memory-probe` проверяет публичный canary в освобождаемых аллокациях: Zeroizing
затирает свой буфер, Automerge оставляет открытые bytes перед dealloc. Поэтому
обычный drop не удовлетворяет требованию очистки. `SecretSession` проверяет другой
вариант: документ живёт в дочернем `secret-worker`, пароль приходит через pipe,
при lock worker сохраняет AEAD-черновик и завершается. Родитель ждёт завершения
процесса и при ошибке черновика. Черновик локальный, не попадает в очередь; его можно
открыть историческим ключом. Родительское/UI содержимое, swap, core dumps и
физическое затирание RAM этим опытом не проверяются; это кандидат границы, не
готовая интеграция Android service или UI.

`network` — отдельная feature, Iroh/iroh-relay 1.1.0, Tokio 1.48.0. Direct использует
RelayMode::Disabled; forced relay отключает IP transports. Самоподписанный локальный
relay разрешён только для loopback теста; отключение TLS-проверки нельзя переносить
в продукт. Поток ограничен 1 МиБ, тайм-аутами и ACK-хешем сохранённого сообщения.
Заблокированный промежуточный процесс не получает пароля или read key.

На Android JNI-стенд `TaypeerNative` передаёт JVM и global Context reference в
`iroh::dns::install_android_jni_context` **до** создания Endpoint. Context живёт
до завершения процесса. Нативный CLI без Context вызывает перехваченную библиотекой
панику и fallback DNS; это обнаружено в первом прогоне, такой запуск не считается
проверенной Android-интеграцией. `app_process` не проверяет разрешения APK, Activity,
WorkManager, Doze или foreground service.

## Незакрытые границы

Общий лимит опыта — 1 МиБ сериализованного файла. File и сетевой read ограничены
до выделения больших буферов. Потокового формата вложений, лимитов decompression
и сложности Automerge, квот истории/ключей ещё нет. Достижение лимита отвергает
запись; исторические ключи и неприменённые пакеты автоматически не удаляются.

Остаются полная схема/вложения, конкурентные писатели, защищённый ОС marker против
полного rollback, Android Keystore/биометрия/lifecycle, реальные телефоны и power-cut.
Короткий fuzzing и инвентаризация advisory/лицензий выполнены, но не заменяют долгий
fuzzing, лицензионную политику продукта и независимый разбор безопасности.
Результаты и точные пределы измерений перечислены в REPORT.md.
